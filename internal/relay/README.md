# 播放链路与验收约定

本文件描述当前实现；`internal/live/README.md` 中按日期记录的实验属于历史测量，不能替代当前能力规则。

## 解码能力由应用提供（2026-11-16）

用户不应自行识别、购买或安装 H.264 / HEVC / AV1 解码器，也不应安装 FFmpeg 或配置 PATH。
应用负责准备播放依赖，并决定硬件与软件解码的取舍。

当前落地：

- FFmpeg / ffprobe 由应用自己取得：首次启动后台下载固定版本
  （BtbN `autobuild-2026-11-02-12-51` 的 win64-gpl 静态包，二进制版本
  `n9.0.2-45-g1e65c6cd5d-20261102`，与本机长期使用的完全相同；包 SHA-256
  `20e6537e…438116` 校验），解出后放进 `%LOCALAPPDATA%\alive\bin`，原子替换，
  失败不留半份副本。安装完成后再执行一次 `ffmpeg -version`，版本号不是
  `n9.0.2-45-g1e65c6cd5d-20261102` 就删除并报错——换包不会静默生效。
  用户不需要安装任何东西，PATH 只在开发机上作为兜底。
- 首次准备约 195MB 压缩包、解出约 200MB，本机实测 57 秒；之后的启动不再下载。
- 播放需要组件但尚未就绪时，界面显示“正在准备播放组件”，组件装好后自动重试当前房间；
  这条路径按本轮启动预算等待，不会把下载时间算成直播故障。
- `ALIVE_FFMPEG_DIR` 可指定唯一来源，供排障与测试使用；设置后不再回落到 PATH。

仍未达到的部分：

- Windows 的实际呈现与声音仍由 MyGo 的 Media Foundation 引擎负责。系统没有 HEVC / AV1
  解码器时，当前做法是用上面这份自带 FFmpeg 解码并转成 H.264 播放——它不需要用户装任何东西，
  但多一次重新编码，起播更慢、画质有损。这不是“自带解码后端”的最终形态。
- 用自带解码器直接出帧的方案已实测：把 FFmpeg 解码的 RGBA 帧接到 MyGo 的逐帧接口，
  本机（Ryzen 7 9700X）1920×1080@60 只能渲染约 48fps，播放约 0.8 倍速，音频会漂。
  故该路线不作为 60fps 直播的交付方案。
- 真正的替代需要一个能接收外部音视频引擎的播放层。MyGo v0.9.0 的
  `ui.NewEngineVideoPlayer` 依赖内部包 `internal/media.Engine`，应用无法实现；
  `ui.VideoDecoder` 只覆盖画面帧，不含声音与时钟。要自带后端（libmpv 或 FFmpeg 库 +
  自带音频输出），需要 MyGo 开放引擎接口或提供等价的原生播放视图，否则只能停在
  “自带解码、系统呈现”的折中。

验收要求：在没有可选 HEVC/AV1 系统扩展、没有全局 FFmpeg 的干净 Windows 环境里，
三种编码都要能出画出声，并覆盖硬解失败转软解、长时间播放与退出清理。
本机格式矩阵不等于这项验收通过。


## 分层职责

```text
播放组件（internal/ffmpeg）
  └─ 定位/自动准备 FFmpeg 与 ffprobe：版本固定、校验落盘，不依赖用户安装或 PATH
       ↓
平台接口（internal/live）
  └─ 真实档位、编码、线路、签名 URL、回源请求头
       ↓ 只解析本次要播的档位；菜单可含尚未解析的项
播放会话（internal/ui/player_media.go）
  └─ 取流预算、会话代次、取消、原生播放器、首帧观测、一次回退、错误终态
       ↓ Variant + Options
传输（internal/relay）
  ├─ transport.go：容器 × 编码 × 原生能力 × 显式开关 → 路径与原因
  ├─ hlsproxy / hlsplaylist：列表预检、地址改写、请求头、原始分片转发
  └─ relay.go：FFmpeg 转封装或转码、本地 HLS、进程与文件寿命
       ↓ 本地 HTTP HLS
MyGo ui/video（Windows Media Foundation）
  └─ 音视频解码、呈现、Ready / Err / Position
```

平台层不决定系统能否解码，播放器不拼接平台协议。传输层不包含平台白名单。
原生解码能力来自系统 MFT 枚举与激活，不从 FFmpeg 能解码、扩展包名字或房间名字推断。
能力结果按编码缓存；回退只禁用当前房间的代理尝试，不写成全局永久禁用。

## 路径决策

| 输入 | 首选 | 兼容退路 |
|---|---|---|
| H.264 HLS，TS 或带初始化段的 fMP4 | 透明代理 | 复制视频转封装 |
| HEVC HLS，系统解码器可激活，fMP4 带 MAP | 透明代理 | H.264 转码 |
| AV1 HLS，系统解码器可激活，fMP4 带 MAP | 透明代理 | H.264 转码 |
| HEVC / AV1 无系统能力，或 TS 包装 | H.264 转码 | 硬件失败后软件编码一次 |
| H.264 FLV | 复制视频转封装 | 显式失败后用户重试 |
| HEVC / AV1 FLV、其他已知编码 | H.264 转码 | 硬件失败后软件编码一次 |
| 编码未声明 | ffprobe 限时探测后重做决策 | 仍未知则保守转码 |
| 显式关闭代理 | 直接走对应兼容路径 | 同上 |

代理只改播放列表的资源地址、补请求头，分片字节原样转发；不会通过降低清晰度提速。
转封装复制 AVC 视频；音频仍按现有兼容策略处理。转码会重新编码视频，不能称为无损或原画直通。

容器与编码必须同时成立：有解码器不代表任意 profile、位深都能播放。
HEVC / AV1 必须有初始化段且不含 TS 分片；master 声明的 CODECS 必须与所选编码一致。
代理仅解开单 variant 包装，最多三层，不能替用户挑多码率 master。
加密、独立音轨、BYTERANGE、低延迟 HLS 等未实现形式交回 FFmpeg；不能吞掉标签后假装支持。

平台选择的约束：

- B 站保留服务端真实 QN、尺寸和码率。另一接口只有 720p AVC 时，不能冒充 1080p 原画。线路按 PATHWAY 标识匹配，兼容完整地址、主机名与 gotcha 短节点 ID。某档没有所选节点时仍使用该档的已有地址，不修改已签名 URL 来制造线路。
- 抖音同一 `stream_data` 档位提供 H.264 或 HEVC HLS 时优先使用 HLS。独立 HLS 地址表不能借用另一来源 FLV 的编码声明；原有默认档位排序保持不变。
- 斗鱼按当前接口取得的实际容器决策。本轮公网样本为 FLV，不代表其 HLS 已验收。
  它还会对匿名请求降档：请求 `rate=0`（原画1080P60）时服务端返回 `rate=4`（蓝光4M），
  换 CDN、把 `hevc` 改成 1 都一样，属于服务端下发限制而不是参数错误。
  播放层会把“点选的档位”和“实际下发的档位”对比，不一致时在画面下方提示
  「该直播间没有「原画1080P60」，已切到「蓝光4M」」，并让菜单显示真实档位，
  不再静默换掉。
- 虎牙当前取流实现仍提供 FLV；本轮没有新增或宣称其 HLS 能力。
- 显式重试重新取流，不用跨重试的签名 URL 缓存掩盖过期地址。

## 启动预算与故障恢复

| 阶段 | 上限与行为 |
|---|---|
| 平台取流 | 40 秒，独立于播放寿命 |
| 传输启动 | 20 秒共享预算，覆盖组件等待、编码探测、代理预检、FFmpeg 启动与内部回退 |
| 缺失编码探测 | 最多 3 秒，受传输剩余预算约束 |
| 代理列表请求 | 10 秒；瞬时网络错误或 502/503/504 等待 100ms 后仅重试一次，共享请求预算 |
| 代理分片请求 | 20 秒；不叠加应用层重试 |
| 代理播放器等首帧 | 打开后 8 秒，仍无首帧则回退一次 |
| 各路径播放器等首帧 | 每次打开后 20 秒；暂停时间不计，Ready 优先于超时 |
| 首帧观测 / 播放后错误观测 | 约 33ms / 250ms，均由 UI 帧调度驱动 |

这些是阶段上限，不是速度目标，也不是一个 20 秒端到端总预算。
系统解码器枚举/激活属于同步原生调用，计时器能取消会话但不能强行中断 DLL 调用；
极端驱动卡死不受这个硬时限保证。硬件编码器共享预热独立完成，每种候选自身有 12 秒探测限制，
单次播放只在自己的剩余预算内等待共享结果。
代理播放器回退会重新启动传输和打开播放器，耗时仍会增加；日志沿用本轮累计时间以暴露这笔成本。
常规起播用首帧实测评估，不能拿“未超过超时”当性能达标。

代理预检失败时立即走兼容路径；打开失败、首帧超时或播放中明确错误也可触发一次回退。
该房间一旦在播放器阶段回退，换档、换线与重试继续使用兼容路径，离开房间后重置。
暂停时不自动重启；恢复播放后才处理已观察到的错误。普通转封装/转码的明确播放器错误，
以及全部路径的最终首帧超时，释放媒体资源并显示可重试错误，保留房间弹幕连接。
直播中但没有任何档位、没有可用地址分别显示明确错误，不永久停在加载或封面。

尚未实现无错误码的持续停帧自动重连：Position 不推进目前只显示卡顿状态。
FFmpeg 在成功交付以后退出的通知尚未直接接入 UI，播放器缓冲耗尽后依赖其 Err 状态；
若 MF 不报错，会落入上述停帧边界。不能把短时观察写成断网恢复或长时间稳定性已通过。

## 静默兜底

选档 / 选线在平台侧对不上时，代码里仍有兜底（用第一档、第一条线路），但一律留痕：

| 位置 | 兜底 | 是否留痕 |
|---|---|---|
| `douyuPickRate` | 标签不在档位表 → 用默认档 | 日志 + 降档提示 |
| `pickVariant`（按需取流之外的平台） | 标签未命中 → 用第一档 | 日志 + 降档提示 |
| `huyaSelectCandidate` | 线路未命中 → 用第一条 | 日志 |
| `biliPickByLine` | 该档没有所选节点 → 用该档已有地址 | 设计如此，注释说明 |

降档提示只在用户主动切档时出现；进房间时的默认档不打扰。

## 资源与诊断

- 每轮持有取消上下文和代次；过期结果不接管 UI，旧代次清理不能停止新会话。
- 取消覆盖预检、探测、子进程、本地 HTTP、未被 UI 接纳的资源；Windows 子进程绑定 Job 寿命。
- 传输启动成功后撤销启动计时器，不用短 deadline 杀死已经播放的直播。
- FFmpeg 正常退出且已有完整列表仍可交付。就绪判定检查列表引用的所有分片，不以目录内任意 TS 文件代替。
- 本地仅监听回环地址，路径令牌限定资源；列表 no-store，HEAD 不消耗首份预取列表。
- 日志记录决策原因、实际方式、取流/传输/打开/首帧累计耗时、声明与解码尺寸。
- FFmpeg stderr 按完整行组装后脱敏；限频输出，失败附最近四行，避免只留下被切碎的组件前缀。签名地址与本地令牌不进入诊断。
