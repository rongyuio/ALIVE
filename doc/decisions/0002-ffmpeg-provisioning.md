# 0002 FFmpeg 随包分发与版本锁定

- **状态**：**落地方式已废止**（2026-11-16）。播放走 libmpv（[0004](0004-libmpv.md)），
  它自带 FFmpeg；兜底路径（relay）也一并删除，我们不再分发任何 FFmpeg。
  本文保留当时的推理与踩坑记录
- **日期**：2026-11-16
- **这条线**：[evolution.md](../evolution.md) 第一条。本文是那场架里唯一没活下来的
  方案——写进文档两小时后，libmpv 把那套下载/校验/落盘整个顶掉了。留着是为了记住
  「自带解码」和「自己写解码器」是两件事。

## 背景

用户不应该关心自己装了哪些解码器。potplayer 安装时会提示装解码器/编码器包，
那是它的历史包袱；alive 不该复制这个包袱。

但播放离不开 FFmpeg：转封装、转码、自带解码、ffprobe 探测全依赖它。
一个"请先安装 FFmpeg 并加入 PATH"的提示，等于把问题丢给用户。

同时还有一个反向风险：机器上可能已经有各种版本的 FFmpeg，如果我们用"找到哪个用哪个"，
同一个 bug 在不同机器上表现不同，线上问题没法复现。

## 候选

### A. 要求用户安装

- 优点：零实现
- 代价：违背"解码能力由应用提供"；版本不可控；PATH 冲突

### B. 随包分发全量二进制

- 优点：版本绝对确定
- 代价：安装包体积增加约 200MB；每次发版都要重新打包

### C. 首次启动后台下载固定版本

- 优点：安装包小；版本仍然确定；可以和校验、原子替换一起做
- 代价：首次使用要等；需要处理下载失败、断点、校验

## 决策

**C，配合版本硬校验和原子落盘。** 固定一个 BtbN 静态包的具体版本，下载后校验
SHA-256、原子替换、失败不留半份副本，装完再执行一次版本号确认——换包不会静默生效。
播放组件还没就绪时界面有「正在准备播放组件」，装好自动重试当前房间。

这套实现随 `internal/ffmpeg` 一起删除了。**换任何解码库都必须重新跑首帧对照**这条规则
留下来了，写在 [third_party/mpv](../../third_party/mpv/README.md) 的升级节和
[measurements.md](../reference/measurements.md) 里。

## 为什么当时不能把 FFmpeg 放进仓库外

**旧 cgo FFmpeg** 的 DLL 是 exe 的加载期硬依赖（Windows 加载器在进程入口点之前就解析
import table），缺了进程起不来，跑不到"启动后发现缺库再去下载"这一步。所以它只能是
构建输入。这条推理写在 [0003](0003-libav-in-process.md)。

现在的 libmpv DLL 是运行时 `LoadLibrary` 加载，不适用这条——这正是它能把 121MB 的
DLL 放在仓库外、构建时再拷进安装包的原因。
