**状态：已落地（2026-11-20）。阶段 0 的定位按 ry 的反馈重写；生产生成器、

## 定位

ALIVE 是桌面直播客户端，四个平台，界面自己画（MyGo），画面是主角。
由此三条，和主题数量无关：

- **chrome 在画面之外消失，在画面之上不抢。** 层级靠明度、间距、字重，不靠装饰。
  静态表面不描边继续有效（`container_test.go` 兜底）。
- **强调色有语义白名单。** 只允许出现在：当前平台/分区、主操作、LIVE、选中/聚焦、
  灵动岛环。其余一律中性。每屏可见强调色 ≤3 处，用截图数。
- **内容不可控，配色与内容解耦。** 直播画面、封面、头像只是不透明矩形；
  决策不读像素；压在它上面的东西必须自带基底；半透明基底按最坏情况证明。

**主题是身份，不是场景。** 一个主题存在的理由是它提供一种不同的色彩气质，
不是"给某类人用"。日 / 夜是同一身份的两曝光，不是两种人格。

## 舒适契约

所有主题、两种模式一视同仁。硬门禁进测试，目标值进证明表。

| 项 | 硬门禁 | 目标 / 理由 |
|---|---|---|
| 夜间地 | L\* 2.5–8.0 | 不纯黑：纯黑配近白字有眩光和拖影 |
| 日间地 | L\* 90–95 | 不纯白：大面纯白在亮环境里刺眼 |
| 夜间正文 | L\* 92–97 | 不用 #fff；近白足够，少一点眩光 |
| 日间正文 | L\* 15–28 | 不用 #000；纯黑压在白底上发硬 |
| 正文对比 | WCAG ≥7.0 | AA 4.5 是地板；APCA 只报告，不门禁 |
| 次级 / 三级 / 元数据 | ≥5.5 / ≥4.8 / ≥4.5 | 元数据目标 5.0；APCA 只报告 |
| 大面彩度 | ≤0.02（地、托盘、卡片） | 大面积带色会显脏、显廉价；强调色不受此限 |
| 表面台阶 | L\* ≥2.3、等分 ±0.5 | 现有规则，继续 |
| 相邻表面 | ΔE00 ≥1.5 | 1.0 是 JND，1.5 留 50% 余量；L\* 仍是主判据 |
| 浮层（`BgElevated`） | ΔE00 ≥1.5 对卡片，或阴影 + 功能描边可证明边界 | 不算阶梯的一档；不靠填充也必须分得开 |
| 强调色 | Ink ≥4.5、Line ≥3、OnInk ≥4.5 | 全部表面，不只地/卡片 |
| 填充上的字 | 普通 3.0 / 显式 2.5 / HC 4.5 | 按填充 L\* 定极性；逐主题可覆盖；低视力走 HC |
| 功能边界 | 对卡片 ≥3（HC ≥4） | `BorderFunctional`；公共 Border 不承担"这里能点" |
| 状态色 | fill / ink ≥4.5 / line ≥3；成功、危险跟随日夜与高对比，在线绿固定 | 语义不变，颜色推导 |
| CVD | 三型模拟后 ink ≥4.5；line / fill 不过 CVD | Machado 2009，severity 1.0 |
| 声明的颜色 | 必须落在 sRGB；量化回差 ΔE00 <1 | Windows 是目标；不声明屏幕显示不出来的颜色 |
| 压内容的涂层 | 纯白 / 纯黑两端 WCAG ≥4.5 | 不采样内容，只算两端 |

## 主题集（提案：6 套 × 日夜 = 12）

六套不是六个色相，是直播间里六样看得见的东西。名字前字是现场物件，
后字是色彩倾向；不看色卡也能猜到大概是什么偏好。

| 主题 | 由来（直播里的什么） | 一眼偏好 | 大面（夜 / 日） | 强调关系 |
|---|---|---|---|---|
| 墨白 | 关灯后的屏幕：画面之外只剩黑底白字和弹幕 | 无彩、字形优先 | 石墨 / 月白 | 光与墨，不带色相 |
| 幕红 | 开播前的幕布与场灯 | 酒红、暖、舞台感 | 深酒红 / 米白 | 幕布红，红为主 |
| 屏青 | 监视器与 CRT 的荧光余辉 | 青绿、冷、屏幕感 | 深青 / 浅薄荷 | 同色系冰青 |
| 灯暖 | 环形补光灯打在主播脸上的暖光 | 暖灰、灯丝光、柔和 | 暖灰 / 奶油 | 灯丝光，低彩度 |
| 科技蓝 | 屏幕冷光与推流信号灯 | 蓝、冷、科技感 | 深海军蓝 / 浅冰蓝 | 科技蓝，同色系高彩 |
| 应援粉 | 观众席的灯牌与应援色 | 珊瑚粉、亮、现场感 | 冷灰 / 浅粉 | 珊瑚粉，高亮 |

**为什么是这六个。** 它们按「看直播时视线落在哪」排列：屏幕（墨白）、舞台（幕红）、
显示介质（屏青）、光（灯暖）、信号（科技蓝）、观众（应援粉）。每一套都能回答
"这个颜色从直播的哪个瞬间来"，不是从别家产品抄一个色相再换名字。

**名字带日 / 夜，但身份只有六个。** 日夜是同一身份的两曝光，由面板上的日 / 夜
按钮切；显示名是「墨白·夜」「墨白·日」，面板直接显示完整显示名。

每套只声明六个输入（地的 Oklch、四档文字明度、强调色 Oklch），
其余继续由 `build()` 推导。日夜各一条独立阶梯：夜间降地彩度、强调色保持高亮；
日间提地明度、强调色压成墨水。两套数值不共用。

面板每侧从 3 格变 6 格（两列三行），不新增开关。高度变化在阶段 2 用
`ui.NewTester` 量，放不下就缩格子，不缩字体。

## 原创性：不抄，也不装作没看过

1. **先写 brief，再取色。** 每套一页：三个形容词、一个材料或光的参照、
   一个强调色关系。brief 里不出现任何产品名。
2. **负参考表。** 把常见产品色板（GitHub、VS Code、Linear、Radix、Material 3、
   Tailwind、macOS 系统色）**连同现有的六套旧配色**转成 OKLCH，按「地 L/C/H +
   字 L/C/H + 强调 L/C/H」六值签名算距离。候选与最近参考的 ΔE00 <5 就重做，
   或者写清楚相似是结构性的、不是沿用的。这是气味测试，不是证明。
3. **不复用现有十六进制。** 六个旧 ID 全部退役；`PaletteID` 落盘值和
   `config_transfer.go` 一并迁移，升级后不回落默认。

### 六条要避开的坑

1. **浅色状态色整体失效。** 四支固定色在浅色地上 1.28–2.33:1，高对比也不改。
   新系统里状态色必须拆 fill / ink / line 并跟随日夜。
2. **`AccentInk` 只在两块表面上验过。** 放到 `FillSecondary`，浅色两套掉到 3.86–3.98。
   新测试必须扫全部表面。
3. **控制条最坏情况不达标。** `rgba(9,10,12,.55)` 压纯白画面，白字 3.06–4.11。
   新系统里任何压在内容上的涂层都要过两端。
4. **功能性描边 1.13–1.76。** 高对比也只到 1.76。功能边界要 ≥3:1 的独立令牌。
5. **色觉缺陷下浅色强调色 3.50–4.03。** 新强调色在三型模拟后仍要 ≥4.5。
6. **声明了屏幕显示不出来的颜色。** ember 的强调色实际差 ΔE00 4.46、彩度少 0.021。
   新 spec 一律落在 sRGB；要宽色域就单独证明回退色，不混在令牌里。

第 7 条是文档漂移：`palette_panel.go` 注释写"背景 / 表面 / 强调"，
`Palette.Swatch` 实际是"地 / 字 / 强调"，顺手改掉。

## 主题切换（2026-11-20）

- 190ms，Oklab 逐令牌混合。根 Box 的 `AnimateTo` 驱动 0→1；新 key 首帧等于目标，
  所以先用 `Jump(key, 0)` 复位，再动画到 1。
- 换目标时 `from` 取**当前显示**（可能已经混合）的调色板，颜色从当前位置继续，
  不回跳。`Blend` 在 t=0 时颜色取起点、`ID/Dark` 取目标，面板的日夜侧当场换边。
- 阴影收进 `Palette`，和颜色一起混；`IslandInk` / `Media*` 是固定墨面，不参与。
- `NonMotion: true`：reduced motion 下仍然是一次颜色交叉淡入，不做位移。
  高对比开关变化直切，不混合。
- 测试：`theme/blend_test.go` 的端点/Oklab 中点；
  `ui/theme_transition_test.go` 的 95ms 中间色、中途换目标不回跳、落点。
- 帧成本未单独计时；每帧约 40 个字段的 Oklab 混合，没有离屏层或模糊。

## APCA：报告，不门禁（2026-11-20）

APCA 是 WCAG 3 草案，阈值会动。已有 WCAG 2.2（普通 4.5、HC 7:1）、CVD 三型、
叠加层两端、状态色三支和舒适契约作为门禁；把 APCA 再钉成 CI 门禁没有净收益：

- 有牙的门禁会要求夜间元数据从 Lc 44–46 拉到 75 上下，整条深色文字阶梯提亮，
  和已确认的观感冲突。
- 没牙的门禁只卡正文/次级，现有配色几乎全过，发现不了新问题。

所以 APCA 只做诊断：

| | 正文 | 次级 | 三级 | 元数据 |
|---|---|---|---|---|
| 夜间 | 91–94 | 69–71 | 54–56 | 44–46 |
| 日间 | 74.9–78.3 | 66.6–69.7 | 66.5–70.2 | 62.4–66 |
| 高对比 | 91–94 | 80–82 | 70–77 | 63.4–74.6 |

唯一有效的信号是 HC 元数据曾只有 56.9–58.8。已经把 HC 的 meta 从
"Sub 与 Meta 的中点"挪到 1/4（系数 0.5→0.25），只动辅助模式；
普通配色不动。复现：`go test ./internal/theme -run TestPaletteAuditProbe -v`。

## 音量组：滑块走强调的墨面那一支，百分比不走（2026-11-25）

控制条浮在画面上，是恒定暗面。音量组两处原来是同一个 `Accent`，现在拆开：

- **滑块填充 = `AccentOnInk`。** 跟配色走，但取的是对 `IslandInk` 推导的那一支
  ——深色主题里它就是 `Accent` 本身，浅色主题里翻成亮的那一支。灵动岛的环用的
  也是它，理由相同：墨面不跟配色变，强调色就必须有墨面版本。
- **为什么不直接 `Accent`。** 真窗口里在墨白·日 下量到滑块 `(0,0,0)`：那一族
  的 `AccentL` 是 0，压在 `playerBarBg` 上就是黑压黑。这不是"颜色不够亮"，是
  根本没有颜色。`internal/ui/player_volume_ink_test.go` 里那套浅色用例正是为此
  存在：注入 `Accent` 后它报 `0/637 个像素是 AccentOnInk {255 255 255}（Accent
  是 {0 0 0}）`。
- **百分比 = `MediaTextDim`，不跟配色。** 数字已经把位置说清楚了，再染一次只是
  把强调色用滥；它比同排图标的 `MediaTextBody` 低一档，层级也更干净。
- 钉住：`internal/ui/player_volume_ink_test.go`，两套配色各跑一遍（幕红·夜 /
  墨白·日），三条判据——填充段 ≥90% 像素是 `AccentOnInk`、百分比区 0 个
  `AccentOnInk` 像素、百分比区确实画出了数字（亮像素数）。
- 反向回归：滑块改回 `Accent` → 浅色用例红；百分比染成 `AccentOnInk` → 两套
  配色都红（199 / 190 个像素）。
- 真窗口（`-tags "mock e2e"`，窗口 2138×1339 设备像素 / scale 1.5，音量 60%）：
  墨白·日 下滑块 `(255,255,255)`、百分比峰值 186 灰、玻璃底 `(69,70,71)`。
