# 0014 关注页直播状态的刷新时机

- **状态**：已落地（2026-11-25）
- **日期**：2026-11-25
- **影响**：`internal/ui/follow.go`、`internal/ui/home.go`（`App` 字段 + Shell 的路由边沿）、
  `internal/ui/watch_media.go`（`windowHidden` 的写者）、`internal/ui/player_media.go`（取流回写）、
  `main.go`（心跳定时器、`OnRestore`）、`internal/diag/diag.go`（`follows.*` 两个事件）

## 问题

关注页的在线状态（绿点 / 排序 / 「正在直播」计数 / 点击进入播放页的预期）只靠
`FollowRecord.Live`。这个字段有两个性质叠在一起：

1. **它落盘。** `state.json` 里存着上次刷到的值，冷启动第一帧直接画出来。
2. **它几乎不被刷新。** 改动前全库只有两个触发点：启动后 1.2s（`main.go`）一次，
   和用户手动点刷新按钮（`follows_page.go` 的圆环）。进入关注页、窗口从最小化
   回来、开着看一整个下午，都不会再刷。

后果不是"慢一点"，是**屏幕在说谎**，而且说得很有说服力：绿点身上挂着一圈
2s 循环的脉冲环，动画本身就等于"此刻正在播"。

同一处的第二个缺陷：`refreshOne` 两条查询链路（房间信息 15s / 取流 20s）都失败时，
写回逻辑是 `f.Live = false`——把"查不到"当成"下播"。启动那一轮正好撞在首屏请求
最挤的时刻，一次网络抖动就能把整张关注列表灭成灰，而那一轮之后没有任何东西会把它
点亮回来（没有重试、没有退避、下次冷启动才轮到）。

第三个：一轮全量刷新最坏可跑十几分钟（100 位关注、6 并发、每人 35s 上限），这期间
`followsBusy` 会把一切再次触发——包括手动点击——静默吞掉，按钮看起来像坏了。

## 决策

### 1. 状态新鲜度是一个显式事实

`App` 上三个字段，只有 `refreshFollows` 的收尾会写；读有两个入口：`followsDue`
判断要不要刷，`followsRetryAfterMS` 只把退避剩余写进日志。

| 字段 | 含义 |
|---|---|
| `followsRefreshedAt` | 上一轮刷完的时刻（零值＝从没刷过） |
| `followsRetryAt` | 失败退避的截止时刻 |
| `followsFailStreak` | 连续失败轮数 |

以前这三件事一个字都没存，所以"该不该刷"这个判断根本无处可做——这才是刷新时机
不合理的根因，不是参数没调好。

### 2. 三条自动路径，各自一个门槛

| 路径 | 门槛 | 为什么是这个数 |
|---|---|---|
| 进入关注页（Shell 求路由边沿） | 30s | 用户从首页过来。半分钟内刚刷过就没必要再打一轮；超过半分钟，主播开播/下播已经可能发生 |
| 窗口从最小化恢复（`OnRestore`） | 60s | 挂机回来比切页更晚，可以更宽容 |
| 关注页可见时的心跳（20s 检查一次） | 90s | 54 位关注跨 4 平台实测一轮 2.82–5.65s（[measurements](../reference/measurements.md)）；检查粒度 20s 让实际间隔落在 90~110s，稳态不到 1 req/s，各平台的 `limiter`（6 并发、60ms 一条）还兜得住 |

手动刷新**不走门槛、不走退避**：用户点了就是立刻要结果。

心跳只在关注页的「关注主播」那一屏生效。订阅分区有自己的列表缓存（`feedTTL`），
观测墙有自己的生命周期（`0011`），两边的节奏都不归这里管——这是"观测墙不动"的
落地方式。

### 3. 查不到 ≠ 下播

`writeFollowStatus(platform, roomID, patch)` 是 `Live` 的唯一状态写入口
（另一处是 `toggleFollow` 新建记录时的快照，那不是"更新状态"）。

`patch == nil`（两条链路都没查到）时**什么都不写**。理由：下一轮刷新本来就会给出
答案，而把绿点灭掉会造出一个不可恢复的错误状态——屏幕说"都下播了"，用户凭什么
知道要手动点一次刷新。

代价说清楚：**主播真的下播之后，如果平台接口恰好全挂，绿点会多亮一会儿。** 这是
有意选的方向——"晚一点发现"好过"错误地宣称没人在播"，因为后者会把用户赶走。

### 4. 全失败才退避

`followSettle` 只在一轮里 `updated == 0 && failed > 0` 时进一档退避
（30s → 2m → 5m → 10m 封顶）。部分成功不退避：数据确实新了，没查到的那几位
下一轮再试。不封顶会让"平台长期不可用"变成永久停摆。

### 5. 取流顺手点亮

播放页取流成功时（`player_media.go` 的 `applyMedia` 闭包）把这一间在关注记录里
置为在播。**只升不降**：能取到地址就是在播的强证据，而"下播"这种降级交给房间
信息那条准（它每次真查 `live_status`，不走缓存）。用户点进去看过的那一位，退回
列表不该还是旧绿点。

### 6. 窗口可见性是一个事实

`App.windowHidden` 只有 `WatchHidden` / `WatchShown` 两个写者（`main.go` 的
`OnMinimize` / `OnRestore` 调它们）。心跳靠它判断"有没有人在看"，不在渲染路径里
回头去问窗口。最小化时 Shell 不重建，界面不推进，刷了没人看还白占带宽。

### 7. 一轮刷新在日志里成对出现

`follows.refresh` / `follows.refresh_done`，带 `reason`（boot / enter / restore /
heartbeat / manual）和 `rooms` / `updated` / `failed` / `retry_ms`。绿点是旧的时候，
第一件事是看这一轮是谁发起、最后查到几条。

## 不变量与它们靠什么检查

| 不变量 | 检查 |
|---|---|
| 退避期内不自动刷、够门槛才刷 | `TestFollowsDue`（表驱动，含边界与退避未到） |
| 退避只会变长、有上限 | `TestFollowsBackoffGrowsAndCaps`（不查数字，查单调与封顶两个不变量） |
| 全失败才退避、部分成功清零 | `TestFollowSettle` |
| **查不到不灭绿点** | `TestWriteFollowStatusKeepsLiveOnFailure`（反向回归：把 `f.Live = false` 注射回去，必须红——已实测红） |
| 写回只命中对应那一条 | `TestWriteFollowStatusWritesMatch` |
| 无窗口 / 最小化时不发请求 | `TestMaybeRefreshFollowsGates` |

## 已知边界

- 心跳的 90s 是量级推导（实测 2.82–5.65s 一轮 + 20s 检查粒度），不是扫出来最优值。
进入页还有一条路：`selectFollowsSection` 从订阅分区 / 观测墙切回「关注主播」时
补一次 `FollowsEntered`，门槛同上。启动的 boot 轮没有门槛，不在三条自动路径里。
  真流下跑一整天看看有没有风控，比现在调参重要。
- 抖音的风控窗口没读，`limiter.block` 的冷却时长如果远大于 90s，心跳会在冷却期
  空转（`acquire` 会等冷却，不报错，只是慢）。
- 面板上不显示"上次刷新于几点"：按钮的 aria-label 就是自动化与读屏的定位入口，
  把它做成随时间变化的字符串会同时打断 `tt.Click("刷新关注状态")` 和读屏节奏。
  陈旧度由日志和三个门槛承担。
- 关注页的刷新只覆盖「关注主播」那一屏；订阅分区的房间列表沿用 `feedTTL`，
  两者语义不同，没有统一。
