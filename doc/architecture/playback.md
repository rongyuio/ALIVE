# 播放链路

一条直播从"用户点了卡片"到"画面上屏"，中间经过哪些层，每层为什么存在，代价是多少。

实测数字见 [reference/measurements.md](../reference/measurements.md)，为什么不用系统解码见
[decisions/0001](../decisions/0001-player-backend.md)，为什么是 cgo 而不是子进程见
[decisions/0003](../decisions/0003-libav-in-process.md)。

## 分层职责

```text
平台接口（internal/live）
  └─ 真实档位、编码、线路、签名 URL、回源请求头
       ↓ 只解析本次要播的档位；菜单可含尚未解析的项
播放会话（internal/ui/player_media.go）
  └─ 起播代次、取消、首帧观测、一次回退、错误终态
       ↓
自带解码（internal/playback）—— 默认，也是唯一的主路径
  └─ 解封装 + 音频解码 + 视频解码，三个 goroutine
       ↓ libav（internal/libav，cgo）
  └─ avformat_open_input / av_read_frame / avcodec_send_packet / avcodec_receive_frame
       ↓
呈现（MyGo）
  ├─ 画面：ui.Bitmap.UpdateYUV（NV12 上传，GPU 做色彩转换）
  └─ 声音：audio.Player（PCM 环就是它的读取源）
```

平台层不决定系统能否解码，播放器不拼接平台协议。

**兜底仍然存在，但换了个位置。** 原先的决策顺序是「代理 → 自带解码 → 转码」，每条路
都可能在主路径上。现在自带解码是唯一的主路径，`internal/relay` 只在它起不来时接手
（无窗口、libav 打不开这条流）。`ALIVE_NATIVE=0` 可以强制走 relay 做对照。

## 时间轴是构造出来的

这是整个改动最重要的性质，也是子进程方案永远做不到的那一条。

直播流本身是**一条**时间轴上的一串包，音视频交错排列，各自带 PTS。`av_read_frame`
按原始顺序把它们交出来，同一个 demuxer、同一个时间基。于是：

- 音画同步不需要任何对齐参数。两路共用一个零点，从第一帧起就是对的。
- 不需要从 stderr 的 `showinfo` 文本里解析时间戳。
- 不需要两个进程各建一条连接、各自探测、各自有起播偏移，再把偏移"补"回去。

零点取**第一个可解码视频帧（关键帧）的 PTS**，音频跳过这之前的部分。理由很实在：
直播流接上之后音频立刻流动，视频要等下一个 IDR，实测斗鱼两者差三秒多。拿音频首帧
当时钟零点，画面就得先干等这三秒——那就是以前首帧 4.5 秒的真正原因。

音频本身的绝对位置由 `audio.Player.Position()` 给出：PCM 环被 WASAPI 按实际出声节奏
消费，"播到哪儿"就是最准的时钟。画面帧按 PTS 对齐到这个时钟上挑。

## 三个 goroutine

```text
解封装   读包 → 按流分到两个包队列（cap 256）
音频解码 收包 → 解码 → 重采样成 48kHz 立体声 → PCM 环（4 秒）→ audio.Player
视频解码 收包 → 解码 → NV12 → 12 个帧槽 → 呈现端按需取
```

**反压只加在音频上。** PCM 环满了，音频解码停下，解封装随之停下——这是唯一会阻塞
整条链的地方。视频那条路永不阻塞：槽满了丢最旧的帧。

这是直播的正确语义。宁可丢一帧画面，也不能让声音断。反过来说，第一版子进程方案
之所以 12 秒断 12 次，就是视频的反压串到了音频上。

视频解码也不全速跑：`free` 槽信号量让它跟着呈现节奏走。不节流的话解码会跑到前面
几秒，槽里堆满未来的帧，反而把当前该显示的那一帧挤掉。

## 缓冲与首帧

两个数，都来自实测而不是感觉，推导写在代码注释里（`internal/playback/engine.go`）：

| 参数 | 值 | 依据 |
|---|---:|---|
| PCM 环 | 4 秒 | 1 秒 → 12 秒断 30 次；2 秒 → 断 27 次、最长空等 888ms；分片是突发到达的，`av_read_frame` 实测会卡 1.63 秒 |
| 预缓冲 | 2 秒 | 播放从直播边缘开始，供给等于实时，缓冲攒不起来；先攒 2 秒再出声，此后 2 秒以内的网络停顿都不会断 |
| 视频帧槽 | 12 | 1080p 3MB/帧、1440p 5.5MB/帧，37~66MB，够吸收一次分片突发又不堆延迟 |

代价是直播延迟多几秒。这是 HLS 本身的性质——浏览器播同一个流也是这个量级，
它没有公开开关可以绕开。

首帧的模型也跟着变了。旧模型是「取流 + 850ms × 拉流次数 + 额外成本」，因为每条路径
都至少拉两次流（探测一次、播放一次）。现在只有一次：

> **首帧 = 平台取流 + 一次连接与探流 + 等到第一个关键帧。**

实测（2026-11-16，本机）：

| 平台与房间 | 首帧 |
|---|---:|
| 斗鱼 8302 | 400ms |
| 虎牙 660000 | 439ms |
| 抖音 218448400833（1440p） | 513ms |
| B 站 7734200（AVC 2K） | 611ms |
| B 站 545068（HEVC 1080p） | 1260ms |

真实窗口里 B 站 545068 从 3648ms 降到 1666ms。

## 断流、丢帧与错误

- **丢帧是设计内的。** 视频槽满丢最旧；呈现跟不上时按 PTS 跳帧。丢的是画面，
  不是信息结构——音频不动。
- **音频断供是唯一的"病"。** 它的来源只有两个：缓冲不够（已按实测定到 4 秒）
  或网络真的断了。`Starved()` / `DemuxStall()` 是诊断这两个的入口。
- **一次回退。** 自带解码起不来（没有窗口、libav 不接受这条流）时回退到 relay
  的兼容路径，只试一次；回退后的失败是终态，不再循环。
- **取消覆盖全部。** 每轮有独立 ctx 与代次；过期结果不接管 UI，旧代次清理不能停掉
  新会话。

## 为什么不再按"能不能解码"选路径

旧设计要枚举系统 MFT、判断 HEVC/AV1 能否激活，再决定走代理还是转码。现在不需要判断：
自带解码用我们自己的 libav，能解什么由链接进来的这份 FFmpeg 决定，与系统装了什么
解码器无关。用户不会因为"系统没装 HEVC 扩展"而看到转码后的糊画面。

这直接回答了 ry 提的那个问题：**解码能力是软件提供的，不是用户要去装的东西。**

## 静默兜底与留痕

| 位置 | 兜底 | 是否留痕 |
|---|---|---|
| `douyuPickRate` | 标签不在档位表 → 用默认档 | 日志 + 降档提示 |
| `pickVariant`（按需取流之外的平台） | 标签未命中 → 用第一档 | 日志 + 降档提示 |
| `huyaSelectCandidate` | 线路未命中 → 用第一条 | 日志 |
| `biliPickByLine` | 该档没有所选节点 → 用该档已有地址 | 设计如此，注释说明 |
| 自带解码起不来 | 回退 relay 兼容路径 | 日志 `native-failed` + 回退原因 |

降档提示只在用户主动切档时出现；进房间时的默认档不打扰。

## 日志

- 用 `id` 关联一轮起播，`ms` 相对本轮起点。
- 首帧可用表示第一帧真正交给呈现端，不是精确的屏幕呈现时刻。
- 记录声明尺寸与解码尺寸，两者不符时以解码结果为准（声明值经常缺失）。
- 签名地址与本地令牌不进入诊断。

## 验收要求

**一台干净 Windows：只装 alive，不装 FFmpeg、不装 HEVC/AV1 扩展。**

- 四个平台各取若干房间，点开即出画出声，首帧 5 秒内
- B 站 HEVC 房间不出转码糊画面
- 连续播放 10 分钟不断音、不停顿
- 退出后无残留进程（现在没有子进程，这一条变成"无残留句柄"）

本机格式矩阵不等于这项验收通过。

工程检查（每次改动播放链路都要跑）：

```sh
make check        # gofmt + build + vet + mygo vet + test
```

`CGO_ENABLED=1` 与测试二进制的运行库搜索路径都在 `Makefile` 里，不用单独设。

原生能力测试另用 `-race -gcflags=all=-d=checkptr=2`。
公网集成用例默认不启用（需要 `ALIVE_LIVE_ROOM`），公网结果来自单独记录的完整 Shell 验收。
