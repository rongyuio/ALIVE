# 测试怎么写、怎么验

`AGENTS.md` 只留了能自动检查的十二条。这一篇放**判断标准**——它不是规则，
是「怎么才算是测住了」。

## 先认清一件事

测试是你写的，代码也是你写的。写代码时理解错了一处，写测试时会照着同一个错误
的理解去断言——**绿得理直气壮，用户一用就崩**。

这个仓库现在就是全绿，用户照样在报 bug。所以判一条测试，别问「它绿不绿」，问两句：

- **期望值从哪儿来？** 来自代码之外，还是来自你脑子里那份和代码一起长出来的模型？
- **按用户报的那个 bug 把代码改坏，它会红吗？**

## 断言的来源，决定测试的强度

| 级别 | 期望值来自 | 特征 | 判定 |
|---|---|---|---|
| L0 | 实现自己 | 同义反复 | 废测试 |
| L1 | 实现内部量（计数器、私有字段） | 重构会红，行为坏了不红 | 只能当补充 |
| L2 | 你自己另写一遍的「应该是 400」 | 你和代码一起错，就一起绿 | 只够防回归 |
| L3 | 代码之外的事实：协议样本、`include/mpv/*.h`、`doc/decisions` 里写死的数、上游实现、物理不变量（面积 / 单调 / 守恒） | 断言有独立出处 | 改逻辑必须有 |
| L4 | 真实运行：真流、真窗口、真文件、真点击 | 用户那条路上到底发生什么 | 改界面 / 播放 / 取流必须有 |

**只有 L0–L2 的改动等于没验证。** 不是态度问题：这几级根本不看代码之外的东西。

## 六类测试，各自能证明什么

| 类型 | 能证明 | 不能证明 | 落在哪 |
|---|---|---|---|
| 纯逻辑表驱动 | 分支、边界、换算、状态机 | 任何与界面、并发、IO 有关的 | 包旁边 `*_test.go` |
| Tester 视图 | 点击、焦点、输入、滚动、动画帧、无障碍树 | 真字体、GPU、图片解码、mpv、内存 | 同上 |
| AST 静态规则 | 「凡是 X 必须 Y」这类跨文件约束 | 运行时行为 | `internal/ui/*_test.go`、`cmd/alive-gate` |
| 帧探针 | 位移、闪现、不静止、像素变化 | 颜色对不对、字糊不糊 | `internal/ui/frameprobe_test.go` |
| 真实窗口 automation | 真渲染、真滚动、真播放、内存 | 1–2 帧的闪（采样约 18Hz）、系统菜单 | 手工，`make e2e` |
| 变异 | 测试本身有没有分辨力 | 需求对不对 | 临时 |

选错类型等于没测：用 Tester 断言「字没糊」，或用截图断言「没闪」，都拿不到证据。

## 六种废测试，直接删

1. **没有断言。** 只构造了一个 Tester、连 `Frame()` 都没调的那种。它永远绿。
2. **常量对照常量。** 断言 `islandPlayerMaxW == 360`、断言三个主题常量等于 B 站
   CSS 的三个数。它们只在有人手改常量时红，而那时改的人本来就会改测试。常量的值
   归注释和设计文档管，测试管行为。
3. **会自己跳过。** `t.Skip("初值不同，这条断言没有意义")`——前提不满足就跳过，
   等于把「没测」写成「通过」。前提不满足应该修场景，修不了就删。
4. **断言私有计数器。** 可观察行为已经测过了，又去断言 `app.followsSeq == seq+1`，
   那只是在钉实现里的代数：重构一动就红，行为坏了却不红。要守「重新进场」，就用
   帧探针看内容层确实重建。
5. **源码字符串 grep 冒充行为测试。** `bytes.Contains` 找标识符，改个变量名就绕过。
   **规则关于结构用 AST，规则关于行为用运行时。**
6. **为了过而调大阈值、超时、容差。** 超时和有像素差都是缺陷报告。每次想改数字时
   重读 `doc/reference/ui-regressions.md`。

另两条容易糊弄自己的：

- **`time.Sleep` 等 UI。** UI 的时间只走 `tt.Advance(d)`；`Frame` 不推进时钟。
  现有那十几处 `time.Sleep` 多数在等磁盘或 goroutine 落地——那是 IO 边界，要带上限
  轮询并在注释里说明。凡是等动画、滚动、双击、tooltip 的，一律 `Advance`。
- **只喂被测函数它想听的数据。** 表驱动要有边界值、异常值、空值；只覆盖 happy path
  的表驱动是常量对照的变体。

## 反向回归，不是先红

「先红」只排除恒真，不证明正确：你写代码时想错的地方，写测试时还会照错。顺序是：

1. **先用真实路径确认行为对**（L4：真窗口、真流、真数据）。
2. 把它固化成测试，期望值抄自代码之外（L3）。
3. **按用户报的那个 bug 把代码改坏一次**——不是随便改，是复现原始错误——测试必须红。
4. 恢复，跑绿。

第 3 步叫「反向回归」：它证明这条测试盯着的是那个 bug，而不是你以为的那个。

新功能没有「改前」可红，所以第 1 步不能省：行为没在真实路径上确认过，就别写测试，
那只是在给自己发合格证。

历史教训：`ls.Key`、`resetListScroll`、`loadRooms` 里的 `ScrollTo` 三处「修复」，
逐个回滚之后测试仍然全绿——那些测试根本没在测它们。

红不出来怎么办：断言写成了恒真，或者场景没走到那条分支。**不要靠改代码去迎合测试。**

## Tester 的硬规矩

权威是 `third_party/mygo/docs/ui/testing.md`。本项目的几条：

- **时间只走 `tt.Advance(d)`。** 从视图外改了状态，先 `tt.Frame()`，再断言或 `Advance`。
- 等条件用带上限的轮询（`player_media_test.go` 的 `waitFor`）；上限只是把卡死变成
  失败，不是可调参数。
- 找元素用 Label 和文本，不用坐标。
- 测试里不发真实请求：`a.Win == nil` 时不发请求、不留后台 goroutine。
- 测试不读真实用户目录（`internal/ui/main_test.go` 的 `TestMain`）。真实的
  `state.json` 能让同一份代码在别人机器上绿、在这台机器上红，而且测试会写回真实
  登录态。新包照做。

## 变异抽查

想知道一个包的测试有没有分辨力，做变异：改一个比较符、一个常量、一个分支，跑对应
测试，期望红。存活的就是没测到的地方。

基线（2026-11-24，`internal/watch/layout.go`，10 个手工变异）：**5 个存活**。
杀死的是 `MaxRooms`、`cols` 上取整、无效 aspect 回落、格内居中；存活的是 `gap`
钳位、初始 `minArea`、格子尺寸下界、同分行数优先、面积比较 `eps`、`contain` 判据。
结论：布局的「形状」被测住了，「选择规则」（同分怎么取舍、边界往哪边倒）没被测住。

**新写或重写一个包的测试时，对最关键的判断至少抽一次变异。** 存活就补测试，
不要补注释。

## 真实窗口那一步

`ui.NewTester` 验不到真实字体光栅化、图片解码、mpv 画面、GPU 合成、内存。命令和
踩过的坑在 [acceptance.md](reference/acceptance.md)。

**它抓不到 1–2 帧的闪**——采样约 18Hz，这是硬限制。别假装解决了，写清楚。
`cmd/alive-framediff` 补的就是这一层（真窗口逐帧录制 + 两段序列逐帧比）。
