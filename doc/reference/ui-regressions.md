# 界面「闪 / 不对」怎么判定

报障的样子通常是「切过去闪一下」「这块不对」。截图是最差的应对方式：它把要找的
东西——两帧之间发生了什么——正好冻结掉。这一篇讲怎么把这类话翻成可判定、可回归
的断言，以及 [0010](../decisions/0010-switch-content-still.md) 之后留在仓库里的那套工具。

**一句话：先把现象翻译成不变量，再写一条在改动前会红的测试，最后才动代码。**

## 为什么截图不行

- **时间分辨率不够。** 用户说的「闪」通常只有 1–3 帧（16–50ms）。手点截图落在哪一帧
  是碰运气，看到了也无法说明是哪一帧、差多少。
- **没有参照系。** 一张图只能证明「现在长这样」，证明不了「这一帧应该等于最终那一帧」。
  人眼说的「看着不对」没有数值，也没法回归。
- **修完没有守卫。** 截图验收通过之后，下一次重构照样能把它改回去，而且没人知道。

截图仍然有它的位置：渲染结果本身错了（颜色、字形、图片解码、GPU 合成）时，帧级
断言看不见「字是不是糊了」。那种情况拍一张，并注明参照帧。

## 四类现象，四条判据

| 用户的话 | 实际是什么 | 判据 | 工具 |
|---|---|---|---|
| 「跳了一下」「抖」 | 帧间位移 | 同名元素相邻帧 bounds 变化 ≤ 0.01 DIP | `probe.shifts` / `RequireNoShift` |
| 「闪一下」「淡入」「发虚」 | 像素在变，位置没变 | 稳态帧之后比对区域像素差 == 0 | `RequireStillAfter` |
| 「卡片先没了一下」 | 元素在某些帧缺席 | 每一帧都在场 | `RequireAlwaysPresent` |
| 「一直在闪」「呼吸」 | 永远不静止 | 稳态后 `FramePending()` 为 false | `tt.FramePending()` |

归不进这四类，就是还没定位。先别改代码。

## 仪器：`internal/ui/frameprobe_test.go`

测试专用，不进正式构建，没有依赖。它逐帧记录被监视元素的 bounds 和指定区域的像素差，
断言失败时打印整张帧表——帧号、元素、坐标、像素数。这就是截图想给的全部信息。

```go
names := cardNames(a.Rooms, 8)                       // 直播间:主播00 ……
p := newProbe(t, tt,
    contentRect(t, tt, names...),                    // 只比内容层
    16*time.Millisecond, names...)
p.Run(40)                                            // 40 帧，不 sleep
p.RequireNoShift(0.01)                               // 不位移
p.RequireAlwaysPresent()                             // 不闪现
p.RequireStillAfter(0)                               // 第一帧之后不再变
```

- **区域必须收窄。** 顶栏的灵动岛有常驻动画，全窗比对永远不静止（见
  [acceptance.md](acceptance.md)：「`--settle` 基本等不到」）。`contentRect` 取一组
  可见卡片的外接矩形，顶栏和控件动画自动排除。
- **只比两帧都在场的元素。** 换代时旧一屏消失、新一屏出现，那不是位移。
- **时间只走 `tt.Advance`。** 探针的 `Step` 内部就是 `Advance(16ms)`，没有
  `time.Sleep`，机器忙不忙结果一样。

## 阈值为什么是这些数

- **0.01 DIP**：远小于 4x 缩放下一个物理像素。任何用户能看见的位移都大于它，
  而布局自身不会有这么大的抖动。
- **0 像素差**：`tt.Image()` 由软件光栅器产出，没有随机源、没有系统时钟
  （`TestProbePixelsAreDeterministic` 守着这条）。所以「相同状态 = 相同字节」
  是精确判据，不需要容差。
- **不要为了让它过而调大阈值。** 超时和差值变大都是缺陷报告，不是阈值不够。

## 先红：唯一的客观证明

一条新测试必须在**改动前**的代码上失败，否则它就是恒真的。三条一起才算证明：

1. 改前红（把失败帧表贴进提交说明 / PR）
2. 改后绿
3. 只回滚源码那一处、保留测试，重新红

实例（2026-11-21，本文件落地时）：把 10 DIP 的入场位移临时加回内容层，
`TestDataArrivalKeepsCardsInPlace` 在帧 2 报 `Δ=0.19 DIP`，
`TestContentLayerStableAcrossSwitches` 在帧 2 报 `Δ=0.19 DIP`，
`TestDataArrivalCommitsFinalFrame` 报整帧像素不等。恢复源码后三条全绿。

`TestProbeCatchesShiftAndFlash` 是仪器的自检：合成一个会动的视图，断言探针确实
抓得到位移和像素变化。它红了说明工具失灵，后面所有绿色都不作数。

## 真实窗口那一层

`ui.NewTester` 看不到图片解码、mpv 画面、真实字形光栅化和 GPU 合成。这一层的做法：

- 用 `make e2e` 起带 automation 插件的构建，`mygo-automation snapshot --json`
  按 ~18Hz 读全部命名元素的 `bounds`，跨样本比对。能抓位移和持续 100ms 以上的闪现。
- **抓不到 1–2 帧的闪**。这是采样频率的硬限制，写清楚，不要假装解决了。
- 只有渲染结果本身存疑时才 `screenshot`，并在验收记录里写明参照帧。

## 新增一条不变量

1. 选类型（上表四选一）。
2. 写场景：窗口尺寸、主题、起始状态、逐条操作，不发真实请求。
3. 期望值从 `internal/theme`、布局公式或上游文档推出来，不读像素。
4. 先跑红；跑不红就重写断言。
5. 修最小的一处。
6. 再跑绿，`-count=20` 结果一致，`make check` 全过。

## 已知边界

- **允许的动效**：tab / 分区滑块、悬停放大、按压反馈。它们不在内容区域里，
  比对区域自然避开；如果你把 region 放大到顶栏，这些会误报。
- **主题切换**是有意的颜色动画（`theme_transition_test.go`），别把它算进
  「稳态后像素不变」的场景。
- **骨架 → 数据**是换了一屏，不是位移：只比两帧都在场的元素，别把旧卡片
  的消失当成闪。
- 新加 `ALIVE_*` 启动开关不属于这里；能用 Tester 就用 Tester。
