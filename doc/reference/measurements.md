三个能用的结论：

- **首帧比窗口晚 8–19ms**，就是一帧的构建时间。窗口一出现画的就是顶栏和网格，
  没有"先黑一下再换画面"的那一段。
- **热启动不比冷启动快。** 磁盘缓存不是瓶颈，瓶颈是平台的分区/列表接口——所以
  再优化缓存也不动这条曲线。
- 第一次冷启动的 1356ms 是首次 TLS 加首个分区接口，之后都落在 230–280ms。
  这是本机、国内网络下的数字，换网络会变。

旧启动层的下限是 520ms 停留 + 240ms 淡出 = **760ms**，比"封面就绪"的 542ms 还长。
它唯一确定做到的事，是让用户多等 200ms 以上。

失败路径（`HTTP_PROXY` 指向死端口，2026-11-18）：错误条在 **120ms** 内出现
（含 `mygo-automation` 一次调用约 50–80ms 的开销），期间顶栏、平台切换、窗口按钮
全部可用。旧版这条路要先盖 2.5 秒，撤层之后才轮到这张错误条。

限制：`mygo-automation` 每次 `screenshot` 约 180ms，抓不到封面那 400ms 弹簧的中间帧。
逐帧证据目前只覆盖到"首帧即应用本体"（e2e 打开会话后 57ms 的那张截里，顶栏和分区栏已在最终位置、网格在半透明入场中），封面入场只有静态截图证明它落在正确位置、不卡不丢。

## 帧成本怎么量（2026-11-19）

MyGo 自带帧统计，不用改代码：

```sh
MYGO_FRAME_STATS=1 MYGO_UNCAPPED=1 ./build/e2e/alive-e2e.exe 2> frame.log
# mygo: 3140 frames a second, uncapped: 0.32 ms a frame
```

`MYGO_UNCAPPED` 去掉垂直同步，帧率反映的是这一帧自己的成本；不加它，帧率会被
60Hz 盖住，看不出余量。`MYGO_FRAME_STATS=1` 还会把超过 8ms 的帧连同各阶段耗时
打成一行，`=all` 连快帧也打。

### 控制条玻璃：量不出差别

2026-11-19，B 站 1080P 原画播放中，1440×900，同一台机器。两种构建各跑两次，
每次取连续 8 秒的每秒采样：

| 构建 | 第一次 | 第二次 |
|---|---|---|
| `glass.Glass{Regular, Tint}` | 0.31–0.36 ms/帧 | 0.62–1.12 ms/帧 |
| 实色 `Background` | 0.42–0.61 ms/帧 | 0.25–0.32 ms/帧 |

**结论：量不出玻璃的成本。** 同一份构建连跑两次的差（0.25 → 1.12 ms）比两种
构建之间的差还大，差异被画面内容（每个房间的码率和场景复杂度）盖掉了。
两组都远低于 16.7ms 的一帧——在这台机器上，这块玻璃是免费的。

要更准的数字，得固定同一个房间、同一段画面，并取更多轮。这次没有，因为
结论已经是"远没到需要担心的量级"。

### 灵动岛流光：真窗口量不到成本（2026-11-20）

岛上的 `Loop` 每帧重画。这一组数是 2026-11-20 早些时候量的：当时环 + 拖影是
两层面具（mask）叠出来的；同一天改成了一笔实色 conic 填色（见
[decisions/0006](../decisions/0006-palette-ladder.md)「光环」一节），mask 那两面
没了，量级只会更小，没有重测。真窗口、真实 GPU 上量一遍：


常驻），连续 8 秒采样。

| 采样 | ms/帧 |
|---|---|
| 最低 | 1.35 |
| 中位 | 2.22 |
| 最高 | 2.32 |

离屏 Tester 的 A/B（带环 2.38ms / 把环短路 2.47ms）本来就在噪声

量级，见 [decisions/0006](../decisions/0006-palette-ladder.md)。

### time-pos 的采样节拍（2026-11-21）

弹幕时钟排查用。探针 `TestProbeTimePosSampling` 在 `.tmp/probes/videosample/`，
不进仓库；片源用 ffmpeg 现生成（1280×720、30fps、H.264 + AAC，8 秒）。起播稳定
0.5 秒后，3 秒内每 1ms 读一次 `Engine.Position()`，统计值变成新值的时间点。

| 项 | 值 |
|---|---:|
| 位置变化次数 | 89（**29.7 次/秒**） |
| 相邻两次变化的间隔 p10 / p50 / p90 / max | 19.8 / 39.2 / 41.1 / 49.5ms |
| 每次变化的增量 p10 / p50 / p90 | 33.33 / 33.33 / 33.33ms |

结论：`time-pos` 只按视频帧更新，不是连续可采样的时钟；每次整跳一帧，间隔在
20–40ms 之间抖。弹幕位置必须以它做「画面在不在走」的判据、以墙钟做步长。拿增量
当步长时，60fps 的界面会得到 `16.7 / 0 / 16.7 / 0…` 的位移序列——这就是「弹幕顿」。
判据与修法见 [decisions/0009](../decisions/0009-live-continuity.md)。

### 软件渲染的三个旋钮

同一档 1080p60，只改 mpv 选项：

| 配置 | 上屏 fps |
|---|---:|
| 默认（bicubic，无 sws-fast） | 41.5 |
| `scale=bilinear` + `dscale=bilinear` + `sws-fast=yes` | **59.3** |

软件渲染是单线程 CPU 做缩放与色彩转换（`render.h` 原话「very slow」），所以这两个旋钮
不是锦上添花，是能不能跑满帧率的分界。

### 试过但不行的

| 尝试 | 结果 |
|---|---|
| 让 mpv 直接输出 NV12 | `MPV_ERROR_NOT_SUPPORTED (-18)`。`render.h` 只认 RGB 单平面格式 |
| `cache=no` | `buffering` 不变，说明不是 cache 水位问题 |
| `--ao=null` | 一样慢，排除音频设备 |
| `video-sync=desync` | 一样慢，排除音频时钟 |
| `hwdec=no` | 一样慢，排除硬解 |
| 等 `Done()` 再开下一个实例 | **5 档卡顿降到 1 档**。上一个实例还占着 WASAPI 时，下一个打不开音频设备，`video-sync=audio` 的时钟停住，整路冻住 |

### 那个 alpha 陷阱

`bgr0` 的第四个字节是未定义值（文档原话「contains uninitialized garbage」，实测 0）。
GPU 采样不看 alpha 所以窗口正常；CPU 光栅化按预乘 alpha 混合，alpha=0 → 整块透明 →
截图里播放区纯黑、UI 其余部分正常。同一份帧，两条路径两种结果。

定位方式：把 `Picture.RGBA` 的产物按像素统计——修之前「非黑 0 / 2073600」，修之后
「非黑 2073337 / 2073600，不透明 2073600 / 2073600」。这个断言现在由
`TestRGBAOpaque` 和 `TestGPUFramesConvertForCPU` 看住。

### 4K60 与 CPU 敏感度（2026-11-16）

平台的 4K 档位可遇不可求，而且会换编码、会下播，拿来当基准不可重复。改用本地推流：
ffmpeg 以 `-re` 把一段 4K60 片源按实时速度循环推成 MPEG-TS，播放器拉
`http://127.0.0.1:8888/live.ts`，解码负载固定。采样 10 秒（当时的探针，已不在仓库）。

| 片源 | 首帧 | 上屏 | 丢帧 | 断供 | 进程 CPU |
|---|---:|---:|---:|---:|---:|
| 4K60 H.264 40Mbps（合成） | 23ms | 59.9fps | 0 | 0 | **1.61 核** |
| 4K60 HEVC 40Mbps（合成） | 24ms | 59.9fps | 0 | 0 | **1.89 核** |
| 4K60 H.264 真实内容（4.3Mbps） | 24ms | 58.5fps | 0 | 0 | **1.47 核** |

**软件渲染能跑满 4K60。** 之前按 1080p 的数据线性外推、得出「4K 撑不住」是错的。

#### 限核（全速 5.43GHz）

| 可用线程 | 上屏 | CPU |
|---|---:|---:|
| 16 | 59.9fps | 1.61 核 |
| 4 | 58.3fps | 1.11 核 |
| 2 | 46.1fps | 0.76 核 |

#### 限频（`PROCTHROTTLEMAX`，全 16 线程）

| 设置上限 | 实际频率 | 上屏 | 断供 | CPU | 每帧 CPU |
|---|---:|---:|---:|---:|---:|
| 100% | 5.43 GHz | 59.9fps | 0 | 1.61 核 | 26.9ms |
| 50% | 1.90 GHz | 59.5fps | 0 | 3.10 核 | 52.1ms |
| 25% | 0.57 GHz | 24.5fps | 8 | 6.12 核 | 250ms |

4 线程 + 1.90GHz（≈ 一颗 1.9GHz 的双核老 CPU）：**55.8fps，丢 0，断供 0**，只掉 7%。

两个反直觉的点：

- **降频 2.86 倍，每帧成本只涨 1.94 倍**（26.9 → 52.1ms）。近一半的活是访存和固定
  开销，不吃频率。所以「核数」不是可比单位——它隐含了「一个 9700X 的核」。
- **限核后每帧反而更快**（16 线程 26.9ms / 4 线程 19.0ms / 2 线程 16.5ms）。线程不跨核
  迁移了，缓存全命中。

结论：门槛约 **5.9 GHz·core 的 Zen5 算力**（1.90GHz × 3.10 核）。近六年任何 2 个以上
现代物理核的 CPU 都不会被这个负载打满。每帧 27ms 的大头是解码 + YUV→RGB + 上传，
不是算力——要拿掉它只能走 GPU 互操作（[0004](../decisions/0004-libmpv.md)），
那是优化项，不是「跑得动」的前提。

**限制**：只有 9700X 是实测；换算到其它型号是按单核跑分比例推算，±20%。表里也没有
UI、弹幕、图片解码的开销，弱机上还要再加 0.5~1 个核。

### 起播时的音画起步（2026-11-16）

mpv 会先把解出来的第一帧显示出来，不等音频管线。低分辨率下两者本来就同时到；4K 上
音频会落在后面，于是出现一段「画面在动、没有声音」。

量法：`playback.Open` 之后每 2ms 轮询，首帧按「画面非全黑」判定（mpv 在视频解出来
之前会先渲染一块黑帧），音频起步按 `time-pos` 离开 0 判定。本地片源是 ffmpeg 生成的
MPEG-TS，由测量程序按指定速率经 HTTP 发出，没有长度也没有时长。

| 片源 | 供片 | 首帧 | 音频起步 | 差（正 = 画面更早） |
|---|---|---:|---:|---:|
| 720p30 2.3Mbps（本地） | 1x | 820ms | 816ms | **−4ms** |
| 1080p60 8Mbps（本地） | 1x | 358ms | 354ms | **−4ms** |
| 4K60 40Mbps（本地） | 1x | 2106ms | 3008ms | **+902ms** |
| 4K60 40Mbps（本地） | 2x | 1077ms | 1511ms | +434ms |
| 4K60 40Mbps（本地） | 8x | 317ms | 407ms | +89ms |
| 斗鱼 475252 原画2K60（真实直播） | — | 180~235ms | 173~231ms | **−4~−6ms** |

所以这是 **4K 且供片跟得上真实码率** 才出现的现象：数据来得越慢，音频管线落后越多。
1080p / 2K 的真实直播完全同步。

`audioGate`（`internal/playback/engine.go`）在「画面已到、`time-pos` 仍为 0」时先不交
画面，预算 2 秒。加门之后：

| 片源 | 首帧 | 音频起步 | 差 |
|---|---|---:|---:|
| 4K60 40Mbps（本地，1x） | 572~595ms | 566~586ms | +6~9ms |
| 斗鱼 475252 原画2K60 | 149~227ms | 145~223ms | +4~6ms |

4K 上那 0.9 秒的画面先行没有了；1080p / 2K 只多等一次 4~6ms 的轮询间隔，起播耗时不变。

**没覆盖到的**：四个平台当前都扫不到 4K 直播间（2026-11-16，斗鱼 8 房最高 2K、
虎牙 8 房最高 1080p、抖音 8 房最高 1440p 级、B 站 45+20 房全部 ≤1080P），所以 4K 的
数字全部来自本地模拟流，没有真实 CDN 上的 4K 样本。

### 斗鱼地址的 5 分钟寿命（2026-11-16）

斗鱼 475252（原画2K60，`hw1a.douyucdn2.cn`，`fcdn=hw`）：

```
expire=300   fcdn=hw
```

`expire=300` 是 CDN 给的连接寿命：到 300 秒服务端主动断开，mpv 把「连接被关」
当成文件播完 → `phase=ended`、`time-pos` 停住。长时播放实测：

| t | 帧数 | pos | phase |
|---:|---:|---:|---|
| 300s | 17765 | 300.1s | playing |
| 310s | 17957 | 303.3s | **ended** |
| 550s | 17957 | 303.3s | ended |

之后四分钟没有一帧，CPU 归零——**画面停在最后一帧，没有错误、没有缓冲提示、
也没有声音**。UI 侧因此什么都不会触发：`stalled()` 只在 `Playing()` 为真时提示，
`Err()` 在 ended 时是 nil。

`expire=0`（仓库里对 `fcdn=ws` 的续期补丁）对 `hw` 线路**无效**：改完 1 帧就
`failed`。所以地址没法续，只能换一份新的。

网页端的做法（`3dd7db01.js`）：`onPlayEnded` 里 `service.destroy()` + 重新取流，
并对 `ON_LOAD_END` 走 `isSmooth`（重连时不显示 loading），`retryLoadTimes` 60 秒
内最多 3 次。

四个平台的写法不一样，`live.expiryFromQuery` 统一认三种：

| 平台 | 参数 | 形态 | 实测寿命 | 网页端 |
|---|---|---|---|---|
| 斗鱼 | `expire` | 剩余秒数 | **300s** | 结束后销毁重开，60 秒内最多 3 次 |
| 虎牙 | `wsTime` | 十六进制绝对秒数 | **300s** | `getProxy` 每 4 秒取一次代理地址，`reconnectCnt` 上限 3 |
| B 站 | `expires` | 绝对秒数 | 3599s | 一小时内不需要换 |
| 抖音 | `expire` | 绝对秒数 | 数天 | 同左 |

我们的做法：`Variant.Expires` 带出失效时刻，播放层提前 60 秒重取一条地址、开好
第二路，出图后再切过去——画面连续，只有声音有一次几百毫秒的接缝。到期没换成功、
或者这一路先停了（`ended` / 时间轴 6 秒不动），走同一条路兜底。

实测（斗鱼 475252，全程 380 秒）：`session.swap_start` 在 241.5 秒，1.7 秒后
`session.swap_done`，全程没有出现 `stream-dead`。

## 旧实现：libav 进程内（2026-11-16，已被 libmpv 取代）

这一节是自研 libav 引擎的数字，保留作对照——放弃它的依据。再往下的「首帧成本模型」「代理路径」「转封装与转码」各节属于
子进程与代理时代，保留作对照和踩坑记录——它们的实现已经不在主路径上了。

同一条流、同一台机器，只解封装一次、音视频共享时间轴。首帧按「平台取流 → 一次连接
与探流 → 第一个关键帧」计；12 秒音频断供指连续播放里 PCM 环见底的次数。

| 平台与房间 | 首帧 | 12 秒音频断供 |
|---|---:|---:|
| 斗鱼 8302 | 400ms | 0 |
| 虎牙 660000 | 439ms | 0 |
| 抖音 218448400833（1440p） | 513ms | 0 |
| B 站 7734200（AVC 2K） | 611ms | 0 |
| B 站 545068（HEVC 1080p） | 1260ms | 0 |

抖音起播 t=300~500ms 有一段设备启动静音，不计入稳态断供。

真实窗口（`mode=native`）：B 站 545068 首帧 **1666ms**，改造前同一台机器 3648ms。

### 缓冲深度是这么定的

| PCM 环 | 12 秒内断供 | 最长空等 |
|---:|---:|---:|
| 1 秒 | 30 次 | 959ms |
| 2 秒 | 27 次 | 888ms |
| 4 秒 | 0 | — |

分片是突发到达的，`av_read_frame` 实测会卡 1.63 秒，所以容量必须明显大于
「分片时长 + 最长空档」。预缓冲再攒 2 秒才出声，此后 2 秒以内的网络停顿都不会断。

### 修掉的结构性问题

| 现象 | 数据 | 原因 |
|---|---|---|
| 12 秒音频断 12 次 | 每次都与视频队列满同时发生 | 视频反压串到了音频：`acquire()` 会阻塞解封装 |
| 视频超前音频 2.5 秒 | 槽里全是未来的帧 | 视频解码全速跑，没有跟呈现节奏 |
| 音画永久错位 | 差三秒多 | 时钟零点取了视频首帧 PTS，而音频已经流了三秒 |
| 斗鱼首帧 4549ms | 关键帧之前的音频白等 | 起播等音频追平关键帧，而不是让音频跳过 |
| 音频时间轴挖洞 | `avcodec_send_packet` 返回 EAGAIN | 收到新包才处理旧包，中间丢包；改为先 drain 再 send |
| 周期性断供 | — | `fflags=nobuffer` 禁止预读；改为 `buffer_size=16MB`、`live_start_index=0` |
| 开代理反而更差 | 开代理断 4~17 次，关代理 0 次 | 本地分片代理在抢带宽；删掉，按需一片一片取 |

最后一条值得单独记：本地分片代理是**净损失**。它把「一条流按需取一片」变成了
「预取六片、缓存、再转发」，浏览器播直播从不这么做——它每次只取当前要播的那一片。
## 首帧成本模型（2026-11-16）

**从零拉一条直播流到拿到第一个可解码画面 = 约 850ms。** 与探测窗口大小无关。

B 站 545068（HEVC 1080P 60fps），同一个签名地址上分别测：

| 实现 | 参数 | 耗时 |
|---|---|---:|
| ffprobe | `-probesize 1000000 -analyzeduration 1000000` | 824ms |
| ffprobe | `-probesize 32768 -analyzeduration 0` | 804ms |
| ffmpeg 解首帧 | `-probesize 32768 -analyzeduration 0 -live_start_index -1` | 912ms |
| Media Foundation（代理路径） | 打开本地 HLS 到首帧 | 866ms |

探测窗口缩小 30 倍只省 20ms —— 说明瓶颈是"建立到 CDN 的连接 + 取播放列表 + 下首个完整分片"，
不是"分析多少数据"。

对照：同轮取流（平台 API）262ms，`ffmpeg -version` 纯进程启动 18ms。

**推论**：每条路径的首帧 ≈ 取流 + 850ms × 拉流次数 + 自己的额外成本。

| 场景 | 首帧 | 备注 |

## 丢帧：从 29% 到 0（2026-11-16）

第一版 1080p60 只有约 50fps、丢 18–29%。逐层排除后是三个独立原因叠在一起：

| 版本 | 丢帧率 | 加了什么 |
|---|---:|---|
| 帧序号 × 声明帧时长 | 29% | — |
| + 起点锚定 | 13.8% | 视频第一帧对齐到当时的音频时钟 |
| + 真实 PTS（`-vf showinfo`） | 7.1% / 21.3% | 用上游给的时间戳，不再自己编 |
| + 正常探测窗口（5MB/2s） | 0.3% | 修掉 `Could not find ref with POC` |
| + 分片缓存（预取 6 片） | **0.0%** | 网络抖动在缓存层被吸收 |

最终：824 / 813 帧两次跑，连续 13 秒每秒 60 帧，一帧不丢；虎牙 FLV 438 帧 0%。

排除链——下面这些全都不是瓶颈：

| 嫌疑人 | 证据 |
|---|---|
| 上屏慢 | `win.Update` 排队 p50=0ms、`UpdateYUV` exec p50=0ms、空视图 1080p 跑满 59fps |
| 解码不够快 | 同一份代码播虎牙 FLV，前 4 秒稳 60fps 零丢帧 |
| 双进程互相拖 | 单进程 54.3fps vs 视频+音频双进程 57.9fps，双进程反而多 |

探测窗口那一条最值得记：压到 32KB 只换来 **20ms** 首帧（824ms → 804ms），代价是从
直播流中间切入时收不全 SPS/PPS 和首个 IDR，HEVC 解码器一路报
`Could not find ref with POC`。同一路流用 5MB/2s 的窗口，15 秒正好 900 帧、一帧不丢。
`internal/relay` 的转码分支用的是同一份参数，同一个 bug。

## 历史诊断案例

这些是失败被定位的过程，留着是为了不重复踩。

### 抖音 13.1 秒就绪、17.1 秒首帧

2026-11-16 00:25。原因有两层：master 播放列表写成
`#EXT-X-STREAM-INF:PROGRAM-ID=1, BANDWIDTH=…`（逗号后带空格），严格属性解析把整条流判为
不支持，于是从代理掉进转封装；转封装用 32KB 探测窗口，在抖音那种碎分片 playlist 上凑不够帧，
ffmpeg 卡在 `not enough frames to estimate rate` 里空转十秒。

修复方式只放宽属性分隔符的空白容错，值内部空格、重复键、缺引号仍然拒绝。
该房间因此重新走透明代理，首帧降到 3.3 秒左右。

**教训**：代理不支持时掉进转封装，代价不是"慢一点"，是十秒级。

## FLV 断流判据（2026-11-22）

探针：`.tmp/probes/ui/`（不进仓库，方法与原始数据见 `RESULTS.md`）。样本是
2026-11-22 抓的 B 站 14709735，HEVC 1080P FLV，60 秒 19.8MB。

方法：本地 HTTP 按 tag 时间戳重放（前 6 秒 burst，模拟 CDN 起播），第 15 秒切换
断法；`playback.Open` 用同一个生产引擎，每 250ms 采 `Position` / `AudioPTS` /
`paused-for-cache`，直接喂生产用的 `watchDeadReason`。

| 断法 | 画面最后推进 | 音频最后推进 | buffering | 判据 |
|---|---:|---:|---|---|
| 完全停发，连接保持 | 15.0s | 15.25s | 15s–结束 | 断流后 20.25s |
| 每 3 秒 1 个 tag | 15.0s | 15.25s | 15s–结束 | 断流后 20.25s |
| 只发音频 tag | 15.0s | 15.25s | 15s–结束 | 断流后 20.5s |
| 视频 tag 照发、负载清零 | 15.0s | 15.25s | 15s–结束 | 断流后 20.5s |
| 关闭连接 | — | — | 无 | 断流后 250ms，播放器报告结束 |
| 停 8 秒后继续供数 | — | — | 15–17.5s | 自己接上，播到文件尾 |

自然播放（无人工干预）：B 站 14709735 180 秒 + 120 秒、斗鱼 252140 120 秒，
缓冲事件 **0 次**，「画面停、音频走」最长 **0 秒**，「两者都停」最长 199ms。

结论：

- FLV 单连接断供时 mpv 连音频一起暂停，`audio-pts` 不再提供「还活着」的信息。
  四种断法里音频都在 250ms 内跟着停。
- 静默断流（连接在、数据不来）不会 `ended`、不会报错：本地盯了 150 秒仍是
  `phase=playing / buffering=true / err=nil`。所以缓冲态必须有自己的上限
  （`streamBufferStallTimeout=20s`）；墙原本就是这个窗口，播放页此前没有。
- 地址寿命（斗鱼/虎牙 300 秒、B 站 3599 秒、抖音数天）走 `Expires` + 提前 60 秒
  热切换，不归这条判据管。

| P3 | `ReduceMotion` 下共享元素过渡是否整体跳过 | 通过：切换第一帧就是终态 |
| P4 | 12 格墙上起飞一次 300ms 的帧预算 | 重建 194µs/帧，飞行 805µs/帧（起飞首帧 516µs），比值 4.2；绝对耗时远低于 16.7ms 预算 |

P1 的含义：过渡期间墙页与播放页同时存在、两个 `Video` 指向同一个播放器，
不会重复解码，也不会画出一块黑。所以不需要"飞行期间不建 `Video`"的补丁。

P4 的比值 4.2 看着高，但基数是 194µs 的整树重建——绝对增量约 0.6ms，
占 60fps 预算的 3.6%。Tester 是软件渲染，绝对值不能外推到真窗口；
这条只用来挡住"量级失控"，不作为性能承诺。

## 暂离与回到墙（2026-11-23，当天两次修正）

探针：`.tmp/probes/wallhidden/`（不进仓库）。目的：**墙看不见之后再回来，
画面多久恢复。** 前两次的结论都错了，原因和数字都记在这里，免得再走一遍。

条件：Ryzen 7 9700X + RX 9070 XT，B 站 7734200，1080P 原画，avc，零拷贝
（墙上就是这条路），每路 16ms 取一帧，隐藏 12 秒，再同时恢复。

### 先修掉的两个缺陷

- **idle 标志写反**：渲染门控进入"跳过渲染"后，`Frame()` 读到的是"没在跳过"，
  于是既不置 `forceRender` 也不唤醒渲染线程。解码如果同时挂着，mpv 不再发
  更新回调，整格就永远不醒，直到墙上 1.5 秒的停帧看门狗把整路重开——
  用户看到的冻帧是几秒到二十秒。修好的是 `plugins/video` 的这一处状态机，
  回归在 `TestFrameWakesAfterIdle`。
- **解码挂起本身不值**：`vd-lavc-skipframe` 把恢复延迟绑到关键帧间隔上（见下表）。
  门控现在只跳渲染，解码继续（`TestRenderGateDoesNotSuspendDecode` 守着）。

### 恢复时间（10 帧连续新画面，不是强制重渲的那一帧）

| 隐藏 12 秒 | 1 路 | 3 路 | 12 路 | 隐藏期间 CPU（12 路） |
|---|---:|---:|---:|---:|
| `skipframe=all` | 21.96s | 21.37s | 未测 | 0.19 核 |
| `skipframe=nonref` | 2.28s | 2.24s | 未测 | — |
| **不挂起解码** | **130ms** | **130–140ms** | **125–141ms** | **0.30 核** |

`all` 的 21 秒不是常数，是"等到下一个关键帧"：B 站这条流的关键帧间隔实测
可到 20 秒。`nonref` 保住参考帧链，但仍要追赶隐藏期间堆下的缓存，约 2.2 秒。

### 为什么之前的"6–37ms"作废

那组数字来自 `cycles.go`：探针手动把 `vd-lavc-skipframe` 设回 `none`，再自己
取帧，绕过了 `Frame()` 的唤醒路径，也没有经过 300ms 门控进入 idle 的那段状态。
它量的是"解码器恢复解码要多久"，不是"用户回到墙要多久"。

### 代价

不挂起解码，隐藏期间 12 路共 0.30 核（零拷贝，第 12 路同时恢复仍是 130ms 级）。
这是拿 CPU 换"回来立刻出画"，只发生在墙还在用的时候（进播放页、最小化）。
离开墙会关掉非焦点会话（2026-11-25），回来走重连，不在这一组数字里。

扩展阅读：`.tmp/probes/wallhidden/resume.go` 是这一次的复现脚本。

## 视频零拷贝（2026-11-23）

探针：`.tmp/probes/gpuzero/`（不进仓库）。目的：**mpv 直接渲进共享 D3D11
纹理，去掉每帧两次跨界**。

条件：Ryzen 7 9700X + RX 9070 XT，B 站 7734200，1080P 原画，avc。
每路 16ms 取一帧，预热 10 秒后量 20 秒。

| 路数 | 软件渲染（`d3d11va-copy`） | 零拷贝（`d3d11va`） |
|---:|---:|---:|
| 6 | 3.58 核 | **0.20 核** |
| 12 | 8.71 核 | **0.40 核** |

约 **20 倍**。省掉的是每帧"显存→内存的拷贝 + swscale 转换 + 内存→显存的上传"，
解码仍由 GPU 完成。`hwdec` 从 `d3d11va-copy` 变成 `d3d11va`，就是这个差别的
直接证据。

真实窗口（`make e2e`，11 格墙）：走零拷贝的格子两秒内 93–99% 像素在变，
没有黑格；`gpu` 日志 19 条（每路一条）。

### 关键实现细节

- **每个引擎一个 D3D11 device**，不是共用渲染器的。mpv 的 `render_d3d11.h`
  写明它用 device 的 immediate context 渲染，而多线程不能同时使用同一个
  immediate context——共用 device 会让 mpv 和渲染器在两个线程上抢同一个
  context，实测表现为整格纯黑。
- 共享纹理带 `SHARED_NTHANDLE | SHARED_KEYEDMUTEX`；mpv 渲染时持 key 0，
  MyGo 的渲染器（`third_party/mygo/internal/gpu/d3d11/video.go`）读时也持 key 0。
- `render_d3d11.h` 已随包放进 `third_party/mpv/include/mpv/`。结构体只有
  一个字段（`void *device` / `void *tex`），之前照记忆多写了字段——不影响
  偏移 0，但不是黑屏的原因，原因是上面那条 context 竞争。

### 未测

- 混合平台/多房间（探针是同一路 12 连接）。
- 4K 源。
- 长时间（>10 分钟）显存增长。
