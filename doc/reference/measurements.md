### 后台收听的画面恢复（2026-11-16）

离开播放页时把视频轨关掉（`vid=no`），只让音频继续；回到播放页重新选轨，
mpv 从下一个关键帧开始解码。`go test ./internal/playback -run TestVideoResume`，
斗鱼 9999「原画」，三轮开关：

| 轮次 | 恢复画面 |
|---|---:|
| 1 | 2.58s |
| 2 | 1.66s |
| 3 | 1.67s |
| 中位数 | **1.67s** |

同一轮里另外验了两条前提，都成立：

- `vid=no` 之后渲染序号停住（画面真的不产出了），而 `time-pos` 继续前进
  （音频时钟没停）——这是后台收听能成立的全部依据。
- 恢复延迟就是关键帧间隔的量级，不是解码器重建。所以它随平台 GOP 变，
  不随档位变。

回来的头 1.7 秒画面停在离开时那一帧，必须给加载提示，不能让它看着像卡死。

### 软件渲染的三个旋钮

同一档 1080p60，只改 mpv 选项：

| 配置 | 上屏 fps |
|---|---:|
| 默认（bicubic，无 sws-fast） | 41.5 |
| `scale=bilinear` + `dscale=bilinear` + `sws-fast=yes` | **59.3** |

软件渲染是单线程 CPU 做缩放与色彩转换（`render.h` 原话「very slow」），所以这两个旋钮
不是锦上添花，是能不能跑满帧率的分界。

### 试过但不行的

| 尝试 | 结果 |
|---|---|
| 让 mpv 直接输出 NV12 | `MPV_ERROR_NOT_SUPPORTED (-18)`。`render.h` 只认 RGB 单平面格式 |
| `cache=no` | `buffering` 不变，说明不是 cache 水位问题 |
| `--ao=null` | 一样慢，排除音频设备 |
| `video-sync=desync` | 一样慢，排除音频时钟 |
| `hwdec=no` | 一样慢，排除硬解 |
| 等 `Done()` 再开下一个实例 | **5 档卡顿降到 1 档**。上一个实例还占着 WASAPI 时，下一个打不开音频设备，`video-sync=audio` 的时钟停住，整路冻住 |

### 那个 alpha 陷阱

`bgr0` 的第四个字节是未定义值（文档原话「contains uninitialized garbage」，实测 0）。
GPU 采样不看 alpha 所以窗口正常；CPU 光栅化按预乘 alpha 混合，alpha=0 → 整块透明 →
截图里播放区纯黑、UI 其余部分正常。同一份帧，两条路径两种结果。

定位方式：把 `Picture.RGBA` 的产物按像素统计——修之前「非黑 0 / 2073600」，修之后
「非黑 2073337 / 2073600，不透明 2073600 / 2073600」。这个断言现在留在 `live_test.go` 里。

### 4K60 与 CPU 敏感度（2026-11-16）

平台的 4K 档位可遇不可求，而且会换编码、会下播，拿来当基准不可重复。改用本地推流：
ffmpeg 以 `-re` 把一段 4K60 片源按实时速度循环推成 MPEG-TS，播放器拉
`http://127.0.0.1:8888/live.ts`，解码负载固定。`TestLocalStream` 采样 10 秒。

| 片源 | 首帧 | 上屏 | 丢帧 | 断供 | 进程 CPU |
|---|---:|---:|---:|---:|---:|
| 4K60 H.264 40Mbps（合成） | 23ms | 59.9fps | 0 | 0 | **1.61 核** |
| 4K60 HEVC 40Mbps（合成） | 24ms | 59.9fps | 0 | 0 | **1.89 核** |
| 4K60 H.264 真实内容（4.3Mbps） | 24ms | 58.5fps | 0 | 0 | **1.47 核** |

**软件渲染能跑满 4K60。** 之前按 1080p 的数据线性外推、得出「4K 撑不住」是错的。

#### 限核（全速 5.43GHz）

| 可用线程 | 上屏 | CPU |
|---|---:|---:|
| 16 | 59.9fps | 1.61 核 |
| 4 | 58.3fps | 1.11 核 |
| 2 | 46.1fps | 0.76 核 |

#### 限频（`PROCTHROTTLEMAX`，全 16 线程）

| 设置上限 | 实际频率 | 上屏 | 断供 | CPU | 每帧 CPU |
|---|---:|---:|---:|---:|---:|
| 100% | 5.43 GHz | 59.9fps | 0 | 1.61 核 | 26.9ms |
| 50% | 1.90 GHz | 59.5fps | 0 | 3.10 核 | 52.1ms |
| 25% | 0.57 GHz | 24.5fps | 8 | 6.12 核 | 250ms |

4 线程 + 1.90GHz（≈ 一颗 1.9GHz 的双核老 CPU）：**55.8fps，丢 0，断供 0**，只掉 7%。

两个反直觉的点：

- **降频 2.86 倍，每帧成本只涨 1.94 倍**（26.9 → 52.1ms）。近一半的活是访存和固定
  开销，不吃频率。所以「核数」不是可比单位——它隐含了「一个 9700X 的核」。
- **限核后每帧反而更快**（16 线程 26.9ms / 4 线程 19.0ms / 2 线程 16.5ms）。线程不跨核
  迁移了，缓存全命中。

结论：门槛约 **5.9 GHz·core 的 Zen5 算力**（1.90GHz × 3.10 核）。近六年任何 2 个以上
现代物理核的 CPU 都不会被这个负载打满。每帧 27ms 的大头是解码 + YUV→RGB + 上传，
不是算力——要拿掉它只能走 GPU 互操作（[0004](../decisions/0004-libmpv.md)），
那是优化项，不是「跑得动」的前提。

**限制**：只有 9700X 是实测；换算到其它型号是按单核跑分比例推算，±20%。表里也没有
UI、弹幕、图片解码的开销，弱机上还要再加 0.5~1 个核。

### 起播时的音画起步（2026-11-16）

mpv 会先把解出来的第一帧显示出来，不等音频管线。低分辨率下两者本来就同时到；4K 上
音频会落在后面，于是出现一段「画面在动、没有声音」。

量法：`playback.Open` 之后每 2ms 轮询，首帧按「画面非全黑」判定（mpv 在视频解出来
之前会先渲染一块黑帧），音频起步按 `time-pos` 离开 0 判定。本地片源是 ffmpeg 生成的
MPEG-TS，由测量程序按指定速率经 HTTP 发出，没有长度也没有时长。

| 片源 | 供片 | 首帧 | 音频起步 | 差（正 = 画面更早） |
|---|---|---:|---:|---:|
| 720p30 2.3Mbps（本地） | 1x | 820ms | 816ms | **−4ms** |
| 1080p60 8Mbps（本地） | 1x | 358ms | 354ms | **−4ms** |
| 4K60 40Mbps（本地） | 1x | 2106ms | 3008ms | **+902ms** |
| 4K60 40Mbps（本地） | 2x | 1077ms | 1511ms | +434ms |
| 4K60 40Mbps（本地） | 8x | 317ms | 407ms | +89ms |
| 斗鱼 475252 原画2K60（真实直播） | — | 180~235ms | 173~231ms | **−4~−6ms** |

所以这是 **4K 且供片跟得上真实码率** 才出现的现象：数据来得越慢，音频管线落后越多。
1080p / 2K 的真实直播完全同步。

`audioGate`（`internal/playback/engine.go`）在「画面已到、`time-pos` 仍为 0」时先不交
画面，预算 2 秒。加门之后：

| 片源 | 首帧 | 音频起步 | 差 |
|---|---|---:|---:|
| 4K60 40Mbps（本地，1x） | 572~595ms | 566~586ms | +6~9ms |
| 斗鱼 475252 原画2K60 | 149~227ms | 145~223ms | +4~6ms |

4K 上那 0.9 秒的画面先行没有了；1080p / 2K 只多等一次 4~6ms 的轮询间隔，起播耗时不变。

**没覆盖到的**：四个平台当前都扫不到 4K 直播间（2026-11-16，斗鱼 8 房最高 2K、
虎牙 8 房最高 1080p、抖音 8 房最高 1440p 级、B 站 45+20 房全部 ≤1080P），所以 4K 的
数字全部来自本地模拟流，没有真实 CDN 上的 4K 样本。

### 斗鱼地址的 5 分钟寿命（2026-11-16）

斗鱼 475252（原画2K60，`hw1a.douyucdn2.cn`，`fcdn=hw`）：

```
expire=300   fcdn=hw
```

`expire=300` 是 CDN 给的连接寿命：到 300 秒服务端主动断开，mpv 把「连接被关」
当成文件播完 → `phase=ended`、`time-pos` 停住。长时播放实测：

| t | 帧数 | pos | phase |
|---:|---:|---:|---|
| 300s | 17765 | 300.1s | playing |
| 310s | 17957 | 303.3s | **ended** |
| 550s | 17957 | 303.3s | ended |

之后四分钟没有一帧，CPU 归零——**画面停在最后一帧，没有错误、没有缓冲提示、
也没有声音**。UI 侧因此什么都不会触发：`stalled()` 只在 `Playing()` 为真时提示，
`Err()` 在 ended 时是 nil。

`expire=0`（仓库里对 `fcdn=ws` 的续期补丁）对 `hw` 线路**无效**：改完 1 帧就
`failed`。所以地址没法续，只能换一份新的。

网页端的做法（`3dd7db01.js`）：`onPlayEnded` 里 `service.destroy()` + 重新取流，
并对 `ON_LOAD_END` 走 `isSmooth`（重连时不显示 loading），`retryLoadTimes` 60 秒
内最多 3 次。

四个平台的写法不一样，`live.expiryFromQuery` 统一认三种：

| 平台 | 参数 | 形态 | 实测寿命 | 网页端 |
|---|---|---|---|---|
| 斗鱼 | `expire` | 剩余秒数 | **300s** | 结束后销毁重开，60 秒内最多 3 次 |
| 虎牙 | `wsTime` | 十六进制绝对秒数 | **300s** | `getProxy` 每 4 秒取一次代理地址，`reconnectCnt` 上限 3 |
| B 站 | `expires` | 绝对秒数 | 3599s | 一小时内不需要换 |
| 抖音 | `expire` | 绝对秒数 | 数天 | 同左 |

我们的做法：`Variant.Expires` 带出失效时刻，播放层提前 60 秒重取一条地址、开好
第二路，出图后再切过去——画面连续，只有声音有一次几百毫秒的接缝。到期没换成功、
或者这一路先停了（`ended` / 时间轴 6 秒不动），走同一条路兜底。

实测（斗鱼 475252，全程 380 秒）：`swap-start` 在 241.5 秒，1.7 秒后 `swap-done`，
全程没有出现 `stream-dead`。

### 内存基线（2026-11-16）

同一台机器、同一个房间（斗鱼 39300，原画2K60 2560×1440），每分钟采一次工作集：

| 场景 | 1min | 2min | 3min | 4min | 5min |
|---|---:|---:|---:|---:|---:|
| 应用，2K | 473MB | 541MB | 542MB | 543MB | **531MB** |
| 应用，1080p（10 分钟） | 416MB | 441MB | 461MB | 479MB | 489MB（10min 仍 489MB） |
| 只开首页、不播放 | 224MB | 172MB | 160MB | 160MB | **160MB** |
| Chrome 独立实例，2K | 1657MB | 1663MB | 1685MB | 1649MB | **1679MB** |

Chrome 那列是单独 user-data-dir 起的一个实例（渲染进程 1080MB / GPU 250MB / 其余 338MB），
页面本身还带着弹幕、礼物、广告和整套前端。

**结论：不是泄漏。** 三条应用曲线都在 2~4 分钟内爬到稳态后持平（Go 堆稳定在 25MB
左右，GPU 专用内存 66MB 不动），涨的是 mpv 的缓冲与解码器、`libmpv-2.dll` 触到的
页、D3D11 纹理。Chrome 在同一个流上是这个应用的三倍。

## 旧实现：libav 进程内（2026-11-16，已被 libmpv 取代）

这一节是自研 libav 引擎的数字，保留作对照——放弃它的依据。再往下的「首帧成本模型」「代理路径」「转封装与转码」各节属于
子进程与代理时代，保留作对照和踩坑记录——它们的实现已经不在主路径上了。

同一条流、同一台机器，只解封装一次、音视频共享时间轴。首帧按「平台取流 → 一次连接
与探流 → 第一个关键帧」计；12 秒音频断供指连续播放里 PCM 环见底的次数。

| 平台与房间 | 首帧 | 12 秒音频断供 |
|---|---:|---:|
| 斗鱼 8302 | 400ms | 0 |
| 虎牙 660000 | 439ms | 0 |
| 抖音 218448400833（1440p） | 513ms | 0 |
| B 站 7734200（AVC 2K） | 611ms | 0 |
| B 站 545068（HEVC 1080p） | 1260ms | 0 |

抖音起播 t=300~500ms 有一段设备启动静音，不计入稳态断供。

真实窗口（`mode=native`）：B 站 545068 首帧 **1666ms**，改造前同一台机器 3648ms。

### 缓冲深度是这么定的

| PCM 环 | 12 秒内断供 | 最长空等 |
|---:|---:|---:|
| 1 秒 | 30 次 | 959ms |
| 2 秒 | 27 次 | 888ms |
| 4 秒 | 0 | — |

分片是突发到达的，`av_read_frame` 实测会卡 1.63 秒，所以容量必须明显大于
「分片时长 + 最长空档」。预缓冲再攒 2 秒才出声，此后 2 秒以内的网络停顿都不会断。

### 修掉的结构性问题

| 现象 | 数据 | 原因 |
|---|---|---|
| 12 秒音频断 12 次 | 每次都与视频队列满同时发生 | 视频反压串到了音频：`acquire()` 会阻塞解封装 |
| 视频超前音频 2.5 秒 | 槽里全是未来的帧 | 视频解码全速跑，没有跟呈现节奏 |
| 音画永久错位 | 差三秒多 | 时钟零点取了视频首帧 PTS，而音频已经流了三秒 |
| 斗鱼首帧 4549ms | 关键帧之前的音频白等 | 起播等音频追平关键帧，而不是让音频跳过 |
| 音频时间轴挖洞 | `avcodec_send_packet` 返回 EAGAIN | 收到新包才处理旧包，中间丢包；改为先 drain 再 send |
| 周期性断供 | — | `fflags=nobuffer` 禁止预读；改为 `buffer_size=16MB`、`live_start_index=0` |
| 开代理反而更差 | 开代理断 4~17 次，关代理 0 次 | 本地分片代理在抢带宽；删掉，按需一片一片取 |

最后一条值得单独记：本地分片代理是**净损失**。它把「一条流按需取一片」变成了
「预取六片、缓存、再转发」，浏览器播直播从不这么做——它每次只取当前要播的那一片。
## 首帧成本模型（2026-11-16）

**从零拉一条直播流到拿到第一个可解码画面 = 约 850ms。** 与探测窗口大小无关。

B 站 545068（HEVC 1080P 60fps），同一个签名地址上分别测：

| 实现 | 参数 | 耗时 |
|---|---|---:|
| ffprobe | `-probesize 1000000 -analyzeduration 1000000` | 824ms |
| ffprobe | `-probesize 32768 -analyzeduration 0` | 804ms |
| ffmpeg 解首帧 | `-probesize 32768 -analyzeduration 0 -live_start_index -1` | 912ms |
| Media Foundation（代理路径） | 打开本地 HLS 到首帧 | 866ms |

探测窗口缩小 30 倍只省 20ms —— 说明瓶颈是"建立到 CDN 的连接 + 取播放列表 + 下首个完整分片"，
不是"分析多少数据"。

对照：同轮取流（平台 API）262ms，`ffmpeg -version` 纯进程启动 18ms。

**推论**：每条路径的首帧 ≈ 取流 + 850ms × 拉流次数 + 自己的额外成本。

## 转封装与转码

| 场景 | 首帧 | 备注 |
|---|---:|---|
| B 站 545068 HEVC 1080P 强制转码 | **3779ms** | 改 `-hls_time 1` 前为 4988ms |
| 抖音 429297252265 原画（曾走兼容路径） | 13.1s 就绪 / 17.1s 首帧 | 见下面的历史案例 |

转码路径的关键帧间隔调过 60 → 30，实测**更慢**（首片 1.6s → 2.4s），已回退。
原因：更短的关键帧间隔让编码器在起播阶段更难在短窗口内稳定出片。

`-hls_time` 只在 `mode == transcode` 时从 2 改为 1（转封装仍保持 2）：
`-c copy` 受上游关键帧限制，改这个没有效果；转码时更短的目标时长能让首片更早落盘。

## 丢帧：从 29% 到 0（2026-11-16）

第一版 1080p60 只有约 50fps、丢 18–29%。逐层排除后是三个独立原因叠在一起：

| 版本 | 丢帧率 | 加了什么 |
|---|---:|---|
| 帧序号 × 声明帧时长 | 29% | — |
| + 起点锚定 | 13.8% | 视频第一帧对齐到当时的音频时钟 |
| + 真实 PTS（`-vf showinfo`） | 7.1% / 21.3% | 用上游给的时间戳，不再自己编 |
| + 正常探测窗口（5MB/2s） | 0.3% | 修掉 `Could not find ref with POC` |
| + 分片缓存（预取 6 片） | **0.0%** | 网络抖动在缓存层被吸收 |

最终：824 / 813 帧两次跑，连续 13 秒每秒 60 帧，一帧不丢；虎牙 FLV 438 帧 0%。

排除链——下面这些全都不是瓶颈：

| 嫌疑人 | 证据 |
|---|---|
| 上屏慢 | `win.Update` 排队 p50=0ms、`UpdateYUV` exec p50=0ms、空视图 1080p 跑满 59fps |
| 解码不够快 | 同一份代码播虎牙 FLV，前 4 秒稳 60fps 零丢帧 |
| 双进程互相拖 | 单进程 54.3fps vs 视频+音频双进程 57.9fps，双进程反而多 |

探测窗口那一条最值得记：压到 32KB 只换来 **20ms** 首帧（824ms → 804ms），代价是从
直播流中间切入时收不全 SPS/PPS 和首个 IDR，HEVC 解码器一路报
`Could not find ref with POC`。同一路流用 5MB/2s 的窗口，15 秒正好 900 帧、一帧不丢。
`internal/relay` 的转码分支用的是同一份参数，同一个 bug。

## 历史诊断案例

这些是失败被定位的过程，留着是为了不重复踩。

### 抖音 13.1 秒就绪、17.1 秒首帧

2026-11-16 00:25。原因有两层：master 播放列表写成
`#EXT-X-STREAM-INF:PROGRAM-ID=1, BANDWIDTH=…`（逗号后带空格），严格属性解析把整条流判为
不支持，于是从代理掉进转封装；转封装用 32KB 探测窗口，在抖音那种碎分片 playlist 上凑不够帧，
ffmpeg 卡在 `not enough frames to estimate rate` 里空转十秒。

修复方式只放宽属性分隔符的空白容错，值内部空格、重复键、缺引号仍然拒绝。
该房间因此重新走透明代理，首帧降到 3.3 秒左右。

**教训**：代理不支持时掉进转封装，代价不是"慢一点"，是十秒级。
