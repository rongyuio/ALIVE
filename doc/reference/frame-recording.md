# 真窗口逐帧录制，两段序列逐帧比对

要证的是「用户看到的那个窗口，某一帧跳了/闪了」。这三层各有盲区，这一篇讲第三层是怎么补上的，
以及它的判据和阈值从哪儿来。

**一句话：把窗口画出来的每一帧从 D3D11 后缓冲回读下来，每帧压成一段独立的 zstd 落成序列
（`record_e2e.go`），再用 `cmd/alive-framediff` 两段逐帧比。**

## 三层采样，各自看得见什么

| 工具 | 采样 | 看到的是 | 看不见 |
|---|---|---|---|
| `ui.NewTester` 帧探针（[ui-regressions.md](ui-regressions.md)） | 逐帧，时钟由 `tt.Advance` 给 | 软件光栅器画的 scene | 真字形、图片解码、mpv 画面、GPU 合成 |
| `mygo-automation screenshot` | ~18 Hz（55 ms 一次） | **CPU 重画**最后一帧的 scene（`Window.CapturePage` → `captureContent` → `windowHost.capture` → `raster.Render`） | 1–2 帧的闪；**「Present 出去的那一帧」**——见下 |
| **本套录制**（`ui.FrameSink`） | **每一次 Present**，一帧不落 | D3D11 swapchain 后缓冲，Present 之前的整帧像素 | DWM 那一层的合成（阴影、系统材质、别的窗口） |

`screenshot` 比想象的强：**mpv 的画面它看得见**。视频在 scene 里是 `scene.Surface`，
带一个 `Restore` 把帧转成 CPU 像素（`internal/scene/surface.go`），所以 CPU 重画照样画得出
视频（实测：同一时刻的 `screenshot` 与录制帧都有一模一样的直播画面）。它真正的盲区是两件别的：

1. **采样。** 55 ms 一次，闪只剩 1–2 帧（16–33 ms）时，采样点落在前后两帧上，看到的是「什么都没发生」。
   这是 [acceptance.md](acceptance.md) 与 [ui-regressions.md](ui-regressions.md) 都写过的硬限制。
2. **它画的是「构建出来的 scene」，不是「那一刻真 Present 出去的像素」。** 重画一遍会把脏矩形、
   Present 时序、驱动实际光栅化这些全部抹平——布局跳了一帧、只有一部分没重画、合成结果和 scene
   不一致，这几种它都会画成「正常」。

### `ui.Recorder`（`plugins/render`）录的是什么

它不是窗口。`ui.Recorder` 用一份自己的 runtime 按调用方给的时刻重建 view，得到
`*scene.Scene`；`plugins/render` 再把 scene 画进一个**永不显示的窗口**（`d3d11.Frames`）
并回读。所以：

- 它确实经过 GPU 光栅化，真字形/真图片/真 mpv 纹理都在里面——比 `ui.Tester` 真实；
- 但它录的是「同一段 view 代码在另一个进程内 runtime 里重建的画面」，**不是用户那个窗口**：
  窗口尺寸/DPI 来自 `RecorderOptions`，时钟是录制器自己的（`recordEpoch` = 2000-01-01），
  焦点、滚动位置、真实数据的到达时机都不在里面。拿它验「用户点下去闪了一下」会漏掉真实状态。

`mygo-automation screenshot` 更近一层，但它是异步采样 + CPU 重画（`raster.Render`），
既不是 GPU 输出，也抓不到 1–2 帧。

### 本套录到的那一层

`ui.FrameSink`（`third_party/mygo/ui/record.go`，本地补丁）在 D3D11 渲染器
`drawFrame` 把整帧画完、DXGI `Present` 之前，用一张 staging texture 把后缓冲
`CopyResource` + `Map` 回读到内存，交给 sink。所以拿到的是**这一帧真正会显示出来的像素**：
shader、混合、圆角裁剪、字形图集、图片、mpv 的纹理都在里面。播放页实测：录到的帧里有
完整的直播画面，且逐帧在变（见下面的实测表）。

两个实现细节值得记着（都写在补丁的注释里）：

- **装了 sink 的渲染器每帧整帧重画**。默认只重画变化的矩形（`Present1` 的 dirty rect），
  而没被重画的部分在 Present 之前还停着更早的帧——回读到的会是混帧。`drawFrame` 里
  `known = ... && r.sink == nil` 就是这一条。
- **sink 为 nil 时成本是一次指针判空**。正式构建里没人给 `ui.FrameSink` 赋值，这条路不存在
  （这两个串在正式二进制里数出来是 0 处，见下面「怎么录」里的实测计数）。

## 怎么录

```sh
go build -tags e2e -o build/e2e/alive-e2e.exe .        # automation_e2e.go 与 record_e2e.go 只在 e2e 里
ALIVE_RECORD=.tmp/rec/a ALIVE_RECORD_SECONDS=8 build/e2e/alive-e2e.exe
```

- `ALIVE_RECORD=<dir>` 开关录不录、录到哪；不给就不录（正式二进制里连这个文件都没有）。
- `ALIVE_RECORD_SECONDS=<秒>` 到点自己收尾。不给就一直录到进程被杀；索引逐帧落盘，
  被杀掉的录制仍然可用（残缺的半帧会被 `alive-framediff` 丢掉）。
- 目录里四样东西：

| 文件 | 内容 |
|---|---|
| `manifest.json` | 宽高、像素格式（BGRA、premultiplied、左上原点）、`frame_bytes`、`format`/`codec`、起点时刻、`first_frame_nonopaque_px` |
| `frames.zst` | 每帧**一段独立的 zstd 帧**，逐帧顺序紧排；第 i 帧的偏移与长度在 `frames.idx` 第 4、5 列。老录制这里是 `frames.bgra`（逐帧紧排的原始像素，第 i 帧在 `i*width*height*4`），仍然读得动 |
| `frames.idx` | 每帧一行：`序号 相对第一帧的微秒 gpu 偏移 压缩后字节数`（老录制只有前三列） |
| `record.log` | 录制纪要：帧率、收尾原因（windowsgui 进程没有控制台，这是唯一的现场） |

`first_frame_nonopaque_px` 是「抓到的到底是不是用户看到的那一层」的实测凭据：ALIVE 的窗口是不透明
的（`d3d11.New`，不走 DirectComposition），实测 0 个半透明像素；哪天它变成非 0，说明窗口改走
premultiplied 合成，比对时要按 alpha 的语义重新想一遍。

`ALIVE_RECORD` / `frames.zst` / `frames.idx` 这三个串在正式二进制里数出来是 0 处（`go build .`
产物按字节数，2026-11-26；老构建里是 `frames.bgra`）；e2e 二进制里是 2 / 1 / 2 处。

## 压缩：每帧一段 zstd

**为什么压。** raw BGRA 是 2138×1339×4 = 11.45 MB/帧，60fps 就是 **690 MB/s**。队列只有 8 格，
写盘跟不上就背压到渲染主线程（`frame()` 里的 `r.queue <- ...` 阻塞），帧率跟着掉。这是「不压缩」
这个取舍的真实代价——不是 memcpy 慢，是磁盘慢。今天这台机器上它不是理论：同一份不压缩的代码连跑
6 次 3 秒录制，`frames.bgra` 写盘量 173 MB/s（被节流时）到 649 MB/s（顺的时候），帧率 15.5–59.1 fps
（表在下面）。压完写盘量降到 1/3 到 1/250，帧率回到 43–59 fps。

**谁在压。** `frame()` 里**一个字都没多**：还是「取一块回收缓冲 → 按行 memcpy → 投队列」。

```
渲染主线程 ──memcpy──> queue(8) ──> 4 条压缩 goroutine ──> results(4)
                                                              │
                                            writeLoop：按序号重排、顺序写、追加索引（唯一碰盘的人）
```

- **压缩不在 `writeLoop` 那一条 goroutine 里**，分成了 4 条。原因是一手测出来的：单条压一帧界面
  2.8 ms（60fps 的预算 16.7 ms，够），压一帧贴满视频的播放页 **37.9 ms** —— 只够 26 fps，而播放页
  恰恰是最常录的。4 条把 37.9 ms 摊成 ~9.5 ms/帧。条数按 `runtime.NumCPU()/4` 取，夹在 2..4
  （本机 8C/16T → 4）。每条一个独立的 `zstd.Encoder`：`EncodeAll` 一次调用只跑一条 goroutine，
  共享一个实例只会把这些调用串行化。
- **每帧独立一段 zstd 帧**，不是连续流。`framediff` 要随机访问第 i 帧，连续流做不到。
- **排序在 `writeLoop`**：压缩结果乱序回来，按序号攒进一个小 map，`next` 凑齐一个写一个。写盘顺序
  因此与帧号严格一致，索引里 offset 单调、`offset+size` 首尾相接（实测 z1/z2/z3 逐条对上文件长度）。
- **队列/回收池**：queue 8、results 4、像素缓冲池与压缩输出池各 `8+2×4=16` 格。在途帧上限约 20 块
  ×(11.45 MB 输入 + ≤11.6 MB 输出)，稳态一般只用 3–5 块。两道工序是并行的（压缩在 worker、写盘在
  `writeLoop`），所以瓶颈是慢的那个：照片页压缩 25 ms/帧 ÷ 4 ≈ 6 ms，写 3.4 MB 在 200–650 MB/s 下
  5–17 ms——都压在 16.7 ms 的预算里。磁盘最差（173 MB/s）时写盘涨到 ~20 ms/帧，正好是实测那组掉到
  43 fps 的原因，队列 8 格（≈133 ms）把这点抖动先吸掉。
- **丢帧仍然不允许**：队列满就阻塞主线程，和压缩前同一条纪律。

**编码参数**：`zstd.SpeedFastest`，单帧一次 `EncodeAll`，CRC 默认开（4 字节/帧，换一个读的时候能
自检的完整性）。选它而不是 `flate`：同一天同一批帧，`flate -1` 压得慢 20–60%、比例还差 1.6–1.8 倍
（界面帧 140 KB 对 77 KB）；`flate -6` 慢 5 倍、只多 30% 比例。

**实测压缩比与耗时**（2026-11-26，Ryzen 7 9700X + RX 9070 XT，Windows 11 Pro，2138×1339，
把真录制里的 12 帧拿出来单量）：

| 画面内容 | 压缩后 | 比例 | 压缩 | 解压 |
|---|---|---|---|---|
| 纯界面（大面积纯色 + 文字，无图） | 45.8 KB/帧 | **250×** | 2.8 ms/帧 | 4.6 ms/帧 |
| 首页封面网格（照片多） | 3.4–3.9 MB/帧 | 3.0–3.4× | ~25 ms/帧 | ~9 ms/帧 |
| 播放页（贴满 mpv 直播画面） | 6.1 MB/帧 | 1.8× | **37.9 ms/帧** | 15.2 ms/帧 |

比例完全由内容决定，所以「压完 1/20」这种话不能说死：纯界面 1/250，照片 1/3，视频 1/1.8。

**录制对比（同一台机器，交替跑，3 秒 × 6 组）**：

| | 帧率（中位 / 最好 / 最差） | 写盘（MB/s） | 每帧字节 | CPU（一个核的 %） |
|---|---|---|---|---|
| 不压缩 `bgra-raw` | 31.8 / 59.1 / **15.5** | 173–649 | 11.45 MB | 38% |
| 压缩 `zstd` | **56.6** / 58.8 / 43.1 | 151–206 | 3.4 MB | 165% |

读法：磁盘顺的时候两者一样（那一组 59.1 对 58.8，帧率没有代价）；磁盘被顶住的时候不压缩的那条
直接掉到 15.5 fps，压缩的那条还有 43–59。**CPU 是代价**：压一帧照片页要 ~1.5 个核（4 条 worker），
这是拿 CPU 换写盘。

盘歇过之后的一次干净录制（2026-11-26 09:24，`make e2e` 产物，`ALIVE_RECORD_SECONDS=3`，
首页封面网格已加载）：**181 帧 / 60.0 fps / `frames.zst` 304 MB**（1.76 MB/帧，6.5×；
同一段前 110 帧还是空骨架，只有 43 KB/帧）。「压前 59.9 fps、压后还是这个量级」就是这条。

**比对端**：`alive-framediff` 按 manifest 的 codec 选读法，两种容器读出来是同一批像素（
`TestCompressedAndRawGiveSameMetrics`）。解压 2–15 ms/帧，256 帧的一段多花 1–4 秒，可以接受。
老录制没有 `codec` 字段，按 `bgra-raw` 认——`.tmp/rec/` 里已经录好的那几段不受影响。


## 怎么比

```sh
# 两段序列（同一剧本各录一次：改前 / 改后，或正常 / 注入）
go run ./cmd/alive-framediff -a .tmp/rec/c1 -b .tmp/rec/c2 -region 8,280,2122,1050

# 一段序列内部：每一帧对某一参照帧（找「第几帧开始跳」）
go run ./cmd/alive-framediff -a .tmp/rec/c2 -ref 200 -from 100 -limit 280 -region 8,280,2122,1050
```

输出是一张帧表（帧号、时刻、位移、平均差、超阈值像素数、占比、判定），末尾给最早出现位移/闪烁的
帧号、参照帧、以及 PASS/FAIL；**有任一帧超阈值退出码就是 1**。开头的 `codec bgra-raw` / `codec zstd`
是这两段各自用的容器——两种容器解出来的像素逐字节相同，可以混着比（`-a` 老录制、`-b` 新录制也行）。

两种模式：

- 给了 `-b`：A 是参照、B 被比。配对默认按 `manifest` 里的时间戳（`-align time`，容许 `-time-tol` 毫秒），
  因为两段录制各自从自己的第一帧起算；`-align index` 就是同号帧。
- 不给 `-b`：A 的每一帧对 `-ref`（默认第 0 帧）。

判据两条，对应四类现象里的两类：

- **位移** = 整帧最佳对齐偏移（`+x` 右、`+y` 下），用横竖两条边缘投影的互相关找，再在 4 像素网格上
  用 SAD 复核。内容整体动了，这个数就是动了多少。
- **像素差** = 未对齐时区域内每像素平均的通道绝对差，以及最大通道差超过 `-pix` 的像素数/占比。
  位置没变、像素在变，就是「闪」。
- 另外顺手给出「对齐后的平均差」（`AlignedMeanAbs`）：它小而原始平均差大，说明「只是挪了」。

`-region` 一定要收窄到内容区。顶栏的灵动岛有常驻动画，全窗比对永远不静止——这条在
[ui-regressions.md](ui-regressions.md) 里写过，这里同样成立。

## 阈值为什么是这些数

**位移 = 1 px**（`-shift-tol`）。录制是设备像素，内容只能按整像素移动，所以 1 px 是位移的最小可表示
单位；而布局层的容差判据是 0.01 DIP（[ui-regressions.md](ui-regressions.md)：4x 缩放下也远小于一个
物理像素）。也就是说 1 px 的整帧位移比布局容差大两个数量级，任何用户能看见的「跳」都超过它。

**平均差 > 0.100、变化像素占比 > 0.010%**（`-mean-tol` / `-changed-pct`）。这两个数来自实测噪音，
不是手感：

| 实测（2026-11-26，Ryzen 7 9700X + RX 9070 XT，Windows 11 Pro，2138×1339 设备像素 @150%，60fps） | 结果 |
|---|---|
| 同一场景两段独立录制，稳态窗口按时间戳配 243 对 | 除注入的那一帧外，**全部 `meanΔ = 0.000`、变化像素 0 个** |
| 同一段录制内，稳态窗口 280 帧对参照帧 | 同上，逐字节相同 |
| 注入 12 DIP（150% DPI → 18 px）单帧位移 | `meanΔ = 52.822`、变化像素 1 439 986 个（64.63%） |
| 播放页（真直播画面，mpv 的帧 → `scene.Surface`），播放中 350 帧 | 位移全程 0 px；`meanΔ` 2.09 → 44.07、变化像素占比到 76% —— 画面在动、位置没动 |

结论摆在这儿：真 GPU 光栅在同一 adapter/驱动/尺寸下是**逐字节确定**的，噪音底是 0。所以阈值取在
「噪音底之上一个数量级、用户能看见的闪之下两个数量级」——0.100 是实测噪音的无穷倍、是一个
卡面大小可见闪烁（300×180 px 变 30 级 ≈ 0.7）的七分之一；0.010% 是 223 个像素，比任何能看见的
闪（一张卡就 5 万像素）小两个数量级。

**不许为了让某一段过而调大。** 差值变大是缺陷报告，不是阈值不够——这一条和
[ui-regressions.md](ui-regressions.md) 的「不要为了让它过而调大阈值」是同一条纪律。

## 灵敏度：它到底能抓到多小的闪

实测（2026-11-26，同上条件）：往渲染路径注入一帧 12 DIP 的整体下移，`meanΔ = 52.822`，
工具在 `(+0,+18)` 报 SHIFT，独立写的另一个算法（直接数整数偏移下不同像素数）在 `dy = -18` 处
不同像素从 1 439 986 掉到 30 388（1.39%）——两个算法互相印证，量出来的 18 px 与
`12 DIP × 1.485` 的物理预期一致。

**一帧（16.7 ms）就够。** 这正是 `mygo-automation screenshot`（55 ms 采样）结构化抓不到的那类现象：
采样点落在闪的前后两帧上，看到的是「什么都没发生」。

**两条判据真的分得开。** 播放页那 350 帧是反面样本：画面里每一帧都在大变（`meanΔ` 2.09→44.07、
76% 的像素在动），但位移全程 0 px。只看像素差会把它当成闪；只看位移会漏掉视频卡住。
真有「跳」的时候位移那一列才会离开 0（注入那一段是 `(+0,+18)`）。

## 已知边界

- **只有 Windows 真窗口有这一层。** `ui.FrameSink` 挂在 D3D11 渲染器上；macOS/Linux 的渲染器不实现
  `SetFrameSink`，sink 装了也不会被调用——录制目录里不会出现 `manifest.json`，`alive-framediff`
  会直接报「不是一个录制目录」而不是默默给个空 PASS。
- **窗口走 CPU 光栅那条路时收不到帧**（`windowHost.present` 的 `drawn in memory` 分支）。WARP
  （没有 GPU 的机器）不算：它仍走 D3D11 渲染器，照样能录。
- **不含 DWM 的合成层**：窗口阴影、系统材质、被别的窗口遮挡的画面都不在里面。好处是「窗口被挡住」
  不影响录到的内容（读的是自己的后缓冲），代价是它不等于屏幕截图的逐像素相等。
- **录制本身有扰动**：每帧一次 `CopyResource` + `Map`（实测 60fps 下不掉帧），加每帧一次 zstd
  压缩（照片/视频页约 1.5 个核，4 条 goroutine 摊开）。写盘量按内容从 11.45 MB/帧降到
  45 KB–6.1 MB/帧（§压缩），这是 60fps 在慢盘上还站得住的原因。帧仍然一帧不少（队列满了阻塞
  主线程，不丢帧），真跟不上时录到的时长会被拉长。
- **压缩解压都是 CPU**：录制端 4 条 goroutine，比对端每帧 2–15 ms。压照片/视频页时 CPU 明显上升，
  这是拿 CPU 换写盘，不是白拿的。
- **比对不懂语义**：换分区、换页面会让整帧都变，工具会照样报 FLICKER。只比同一屏的稳态窗口，
  或者用 `-region` 收窄。
- **单位是设备像素，不是 DIP**：150% DPI 上 12 DIP 的位移读作 18 px。报告里写数要连 DPI 一起写。

## 一次完整的验收长什么样

```sh
# 1) 录改前：首页停留几秒 + 切一次分区
```
