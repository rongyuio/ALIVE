# 演化史：五条线

这个项目 11 天、421 次提交、170 个 `fix:`。它不是一个功能列表，是**五个问题被反复
处理**的过程。这份文件把它们连成线。

## 为什么要有这一份

决策文档记的是「决定了什么」。但读它的人真正需要的是：**这条路走过几遍、在哪儿
拐弯、拐错了几次**。散在 15 篇 `decisions/` 里的过程拼不成一条线——它们各自为政，
每篇都说「已落地」，没有一篇说「三天后又推翻了」。

一份只写结论的决策文档，会让人以为事情一次就做对了。

看这条线的用法：改代码之前，先在这里找到你踩的是哪条线，再看那条线已经试过什么。

## 一、播放器：一天里三次转向（2026-11-16）

```
00:47  e8ae650  feat: 应用自带并自动准备播放组件
02:43  989406a  feat: 新增自带解码播放会话
07:08  ce9e4ff  feat: 引入 libav 进程内解码
07:09  7731782  refactor: 播放引擎改用 libav，删除子进程与分片代理
07:09  0f4284c  docs: 播放链路文档重写为 libav 进程内方案
09:09  6fcbdec  feat: 入库 libmpv 运行库与 video 插件骨架
09:10  7a55d61  refactor: 播放引擎改用 libmpv，删掉自研的解封装与调度
10:24  0c9a548  refactor: 删除 relay 兜底与 ffmpeg 组件
```

**当天以为 → 实际**

| 当时以为 | 实际 |
|---|---|
| 问题是系统缺解码器，包一份 FFmpeg 就好 | 是 Media Foundation 的 HLS source 为点播设计，延迟底噪 6–9 秒 |
| 走自带解码就是自己写一套 | libmpv 已经写好了，我们只是要一个能自己实现引擎的接口 |
| 子进程拆音视频能对上轴 | 拆开的那一刻同步就丢了，反压还串成一条 |

**两次白干**：07:09 写下的「首次启动下载固定版本 FFmpeg」整套方案（校验、原子落盘、
版本硬匹配），两小时后随 `7a55d61` 作废。09:20 那天把 `third_party/ffmpeg`（143MB）
从仓库删掉。

**最有信息量的一次实测**：落地 libav 后以为瓶颈在上屏（1080p60 只有约 50fps），
逐层排掉才发现是三个自己的实现错误叠在一起——探测窗口压到 32KB 导致缺参考帧、
呈现时刻用「帧序号 × 声明帧时长」推算、解码进程直接读 CDN 没有任何缓冲。修完
1080p60 零丢帧，**上屏从来不是瓶颈**。

**结论落在**：[0001](decisions/0001-player-backend.md)（取舍）、
[0003](decisions/0003-libav-in-process.md)（为什么放弃子进程，那三条结构性错误）、
[0004](decisions/0004-libmpv.md)（终局）。
[0002](decisions/0002-ffmpeg-provisioning.md) 是这条线唯一的墓志铭。

## 二、配色：从「挑六套」到「让颜色可推导」（2026-11-18 → 11-20）

```
11-18  0006 定案：颜色由六个输入推导，对比度写进 make check
11-19  82ee45d  feat: 接高对比、加深浅色地面、控制条换真玻璃
11-19  8d0d5bf  feat: 面板也上玻璃，画面上的墨收进令牌
11-19  7d10b2f  fix: 顶栏两处容器底色不一致；阴影收成两级阶梯
11-20  11:28 → 13:06   两小时内 10 次提交，全部是配色
11-20  ee8288f  feat: 换用六族十二套配色与状态色三支
```

**认知修正**

旧六套的问题不是「不好看」，是三件事叠在一起：四套配色的卡片色是复制粘贴的
（`ember` 的暖黑底配了 `signal` 的冷蓝卡片）、`TextMeta` 在每套里都至少挂一个表面
（19 对低于 4.5:1）、浅色主题的品牌色在白卡片上 ≈1.1:1。

真正的解法不是「再挑六套」，是**让颜色可推导**：每套只声明六个输入，其余由 `build()`
算出来，对比度写成测试。`TestSurfaceFamilySharesHue` 当场抓出 `mono` 和 `ember`。

**代价**：11-20 那两小时的 10 次提交里，有 5 次是改名（`电子蓝→科技蓝`、
`日间粉→亮珊瑚`、`主题集改为直播现场命名`）。那是设计迭代，不是工程——但它逼出了
「六族 × 日夜」这个结构，所以不算白干。

**结论落在**：[0006](decisions/0006-palette-ladder.md)（生成器思路）、
[0008](decisions/0008-palette-system.md)（六族十二套与舒适契约）、
[palette-briefs.md](reference/palette-briefs.md)（每族的身份与 LCH 输入）、
[palette-ladder.md](reference/palette-ladder.md)（表面三档与灵动岛几何）。

## 三、直播为什么卡：八轮排查（2026-11-16 → 11-22）

完整记录在 [0009](decisions/0009-live-continuity.md)，那是全仓库最好的一份排查记录
——它每一轮都写「提出假设 → 预注册判据 → 实测 → 推翻上一轮」。

```
第一轮  缓存参数不够 → 否掉：冻结的因果在上游空档，不是 mpv 配错
第五轮  对照网页端实际请求 → 发现 HLS 每片新建连接、playlist 轮转时跳片
第六轮  换成 FLV → 问题消失  ← 根因在这
第七轮  取流拆成「列菜单」与「解析地址」 → 墙才开得起来
第八轮  断流判据按 FLV 实测收紧
```

**认知修正**：直播卡不是「缓存不够」。加深缓存（`live_start_index=-5`）确实能吸收
更长的空档，代价是等量的延迟——而空档本身来自上游，加深缓存只是把它藏起来。

**这条线的方法论比结论更值钱**：「先写死判据与预算，再看数；不把重构当默认答案」。
0009 里那句「这一条后来被否掉了一半」，是这个仓库里唯一一处公开承认自己的判断错的
地方。

最长的一条线，六天，一百多次提交，战场文件是

```
11-22  ac6c14f  fix: 同一间房不再有两个引擎，离开墙不再立刻关会话
11-22  1246acc  fix: 观测墙会话交接的三处所有权漏洞

11-23  fb5b87d  feat: loading/err 收进 roomSession
11-24  8c6883e  refactor: 焦点收成单一写者，音量与播放态住进会话
11-24  5d4dbcc  refactor: 音量和引擎关闭收成单一写者
11-25  775fa3e  fix: 从墙上带进播放页的一路补齐媒体轮次
```

**六次，同一个病**：某个事实存了第二份。

每次修完都以为修干净了，下一轮又冒出来——因为**每修一条路径就加一个判断**，
下一条路径撞上没覆盖的组合，就是新 bug。11-22 那天最典型：上午修完「同一间房不再
有两个引擎」，晚上又抓出「会话交接的三处所有权漏洞」，第二天再收 `roomSession`。

**认知修正**：真正的解法不是补判断，是**收成单一写者**，然后用测试钉住：
`TestNoSecondPresentMechanism`、`TestNoSecondFocusWriter`、`TestNoSecondVolumeWriter`、
`TestNoSecondEngineCloser`。

这条线的结论写进了 `AGENTS.md` §3.7，包括那条「同一个文件 7 天内第三次 `fix:` → 停手」。

**结论落在**：[0011](decisions/0011-watch-wall.md)（起点）、
[0012](decisions/0012-surface-model.md)（拐点）、
[surfaces.md](architecture/surfaces.md)（模型与七条不变量）、
[watch.md](architecture/watch.md)（墙的实现）。

## 五、观测墙能不能同时扛十二路（2026-11-21 → 11-25）

```
11-21  记录四平台 9 路并发实测
11-22  画布回到精确 16:9，格子四周不再露黑边
11-23  13:34  b9d00a7  wip: 视频零拷贝的骨架（D3D11 render API），默认关闭
11-23  13:56  ba083ef  perf: 视频零拷贝，12 路墙上从 8.7 核降到 0.4 核
11-23  3b7a327  feat: 暂离默认不拆会话，看不见只意味着不渲染
11-23  c4beeb0  perf: 没人看时同时挂起视频解码，回来 6–37ms 接上
11-23  93a6935  fix: 回到墙不再冻帧：门控唤醒写反了，解码不该挂起
11-25  d0f2283  feat: 去掉观测墙的「暂离时省流量」开关
```

**认知修正**：12 路的瓶颈不是带宽，是**每帧两次 CPU↔GPU 跨界**。D3D11 共享纹理
把 8.7 核压到 0.4 核。

**自己打自己**：「暂离时挂起解码」是 11-23 上午的结论（6–37ms 接上），当天下午就被
「门控唤醒写反了」推翻；11-25 又把衍生出来的「省流量」开关整个删掉。这条线上**同一
天内两次自我修正**，数字都在 [measurements.md](reference/measurements.md) 的
「暂离与回到墙」里，包括那句「为什么之前的 6–37ms 作废」。

## 这份文件本身

- 加一条线：它必须**跨三天以上、有至少两次自我推翻**。一天解决的不叫线。
- 每条线必须有「当时以为 → 实际」。只有时间表的线是流水账。
- 数字不抄这里，指到 [measurements.md](reference/measurements.md)。
- 线的终点写「结论落在哪几篇」，那是下一层文档的指针。
